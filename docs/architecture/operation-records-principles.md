# 操作记录：长期约束

本文定义操作记录的存储、可见性与输出边界；组件用法见[操作记录组件](../../framework/docs/components/operation-records.md)。

## 1. 两个 genre 不可混为一谈

审计日志面向取证，操作记录面向业务管理者与客服，回答“这个对象发生了什么”。本仓以业务动作而非 HTTP 请求为单位，主列显示可读句子，技术字段留在详情；若一行等于请求或主列全是 URL、状态码与耗时，已退化为技术日志。

操作记录仍记失败与拒绝，`Outcome` 独立存储和筛选。依据是 OWASP 的 action、affected object、result status、reason 维度，以及 NIST AU-3 的成功/失败标识；不能把结果只塞进句子。需求归属按受众与举证责任判断，不按界面外观判断。

## 2. 存渲染后的句子 = 语言永久锁死

本仓支持中英双语，业务动作与失败原因须按读者语言渲染，不能在写入时固定语言。

### 2.1 反面证据

美团 `mzt-biz-log` 先渲染模板再落库，若依把中文标题写入注解，均固化写入语言。Zulip 在发送时翻译后存消息，导致其他语言的读者看到发送者语言（[问题 #19730](https://github.com/zulip/zulip/issues/19730)）。这些方案不适合本仓按读者渲染的要求。

### 2.2 正面证据

Django [1.10 发行说明](https://docs.djangoproject.com/en/5.2/releases/1.10/)明确改为存 JSON 变更结构，访问时按当前语言翻译；旧句子仍无法改变语言。Discourse 的英文 `Removed %{who} %{when}` 与中文 `%{when}移除了 %{who}` 顺序不同，说明必须翻译整句并使用具名占位符，不能拼接翻译片段。飞书以稳定事件码提供中英文描述，也采用码与显示文本分离。

### 2.3 由此固化的四条约束

1. 业务叙述存动作码、错误码和具名参数，不存渲染句子；技术失败详情是显式提供的安全诊断文本，不作为本地化业务叙述。
2. 整句进语言包，使用具名占位符，不拼接翻译片段。
3. 筛选维度与可见列独立，避免可读展示限制查询和导出。
4. trace、目标 ID 与授权依据放详情，不进主列。

## 3. 注解路径刻意不回填目标名，这是安全属性

授权拒绝时调用方无权访问目标，不能为显示句子查询目标名并写入可读记录。因此注解只收标识，不增加名字参数；被拒记录只显示 ID。此安全边界须写入注解 XML。

名字规则：

- 目标名取非空可读字段：角色 `DisplayName ?? Name`，用户 `DisplayName ?? Username`。
- 操作人名取主体 `name`，缺省退到用户名；签发时 `name` 写显示名、`preferred_username` 写用户名。
- 操作人名与目标名都存快照，避免改名或销号后反查得到不同结果。Django 的 `object_id` / `object_repr`、Jira 的 `from` / `fromString` 同样分存标识与当时文本。

## 4. 可见性分层与模拟登录透明度

记录可见性仅在租户全局过滤器允许的记录内生效：

| 层级 | 谁能看 |
| --- | --- |
| `Tenant` | 当前租户或宿主层内的读者 |
| `Host` | 仅宿主读取范围 |
| `Actor` | 租户读取范围只见本人（ActorId、ActorTenantId 同时匹配）；宿主读取范围可见 |

读取权限由端点策略把守，查询服务本身不做授权。无租户上下文时只读宿主层（`TenantId` 为空），在该层内可看全部可见性级别；查看租户层须切入该租户上下文，按租户读取范围筛选。`Host` 范围不关闭租户过滤器，也不跨分库聚合。

`Host` 记录必须在宿主层：租户上下文的失败写入宿主库，来源租户存 `ActorTenantId`；成功直接报错，因为成功记录须与租户业务事务同生共死。这类成功动作应登记为 `Tenant`，或切到宿主上下文执行。

技术失败详情、链路标识与 `ActorTenantId` 仅下发给宿主读者，服务端裁剪，不能只在界面隐藏。技术详情仍须由调用方确认可以公开，不写原始异常消息或 `exception.ToString()`。

查询可见范围必须显式指定：`Host`、`ForTenantReader` 或 `Unrestricted`；最后一项只供不代表读者的内部任务，不能用默认值替调用方决定安全边界。

模拟登录须对租户透明：

- 同一次模拟在两层各留开始与结束：租户侧 `impersonation.started` / `.ended`（目标账号），宿主侧 `tenant.impersonation-started` / `-ended`（目标租户，`Host` 可见）。分库场景不能靠一条跨层可见记录替代。
- 模拟期间操作人名是被模拟者，模拟者名是真实操作人，两者都对租户可见；签发声明名须与记录器一致。
- 结束时请求主体仍是被模拟者；写宿主侧记录前切回发起人主体，保证 ActorId 正确。
- 界面须有明显视觉区分，避免把模拟者动作误认成租户用户本人动作。

## 5. 未登记动作写入即报错

动作码须登记类别、可见性与严重度，未登记即抛错，不用默认可见性兜底。读取不再登记的历史码时显示裸码，筛选项按读者可见性裁剪。失败记录独立提交，见[组件实现行为](../../framework/docs/components/operation-records.md#实现行为)。

## 6. 保留期：搬运而非删除

数据库记录默认只增不减。保留期须显式配置，到期搬入归档表，不通过本组件删除；彻底销毁需独立授权。日志模式的采集、保留与销毁由宿主日志平台负责。

后台归档须[显式处理全局过滤器](./isolation-and-authorization-scenarios.md#后台作业过滤器的方向会反过来咬人)。`IgnoreQueryFilters()` 只覆盖当前物理库；分库记录须通过 `ITenantDatabaseEnumerator` 枚举宿主库与独立库，逐库执行并隔离失败。

## 7. 该记什么

改变账号身份、权限或业务数据的动作，以及对应失败与拒绝，均须记录“谁、何时、做了什么、结果如何、凭什么”。高频失败的容量策略由宿主明确制定，不能默认为不记；采样与次数汇总属于宿主策略，组件不内置。时区、语言等个人偏好不改变这些对象，不记。

## 8. 输出与内置历史分别组合

数据库历史与结构化日志是同一套记录器、动作定义和安全调用链的两种写入方，Framework 只提供契约与适配器，Core 不依赖 EF 或 Web，也不感知模板角色与条件；查询端点与归档由宿主显式组合。两种模式的提交时序与持久化保证见[操作记录组件](../../framework/docs/components/operation-records.md#结构化日志输出)：日志模式有“提交后、输出前退出”的丢失窗口，不能描述为数据库模式的等价保证。模板关闭内置历史只裁剪数据库历史、读侧产品与界面，仍保留结构化安全事件、实体审计、软删除、账户锁定与会话撤销。

## 9. 刻意不做的能力

- 不提供字段级 diff，也不预留没有实现支撑的标记。需要时由独立组件提供变更追踪，审计字段须 allowlist，防止密码哈希、安全戳与令牌落库。
- 不做哈希链：空列无完整性保证，写入时读取上一条会串行化追加；先收敛数据库权限。将来启用链时，只能覆盖启用后的记录。
- 索引按真实慢查询添加；追加表每个索引均增加写入成本，不为猜测的查询模式预建。

## 10. 失败去重的载体

端点兜底按 DI 作用域登记的"动作码 + 目标"（`RecordedFailureTracker`）跳过已由应用服务记过的失败。作用域代表"这次拒绝"并不严格，留有三处边界：跨作用域解析记录器时多记一条；端点推不出目标且同一请求以同一动作码再次失败时少记一条；注解与应用服务的目标拼法不一致时多记一条。三处都需要宿主写法不一致才触发，边界写在组件契约里，当期不换载体。

候选是把标记打在被拒绝的异常实例上：能消掉跨作用域与同动作码两处边界，但依赖异常身份不被包装替换，且载体归属未定（放 `BusinessException` 让异常组件长出审计语义，放 `Exception.Data` 与"`Exception.Data` 不进记录"冲突）。出现以下任一情况再评估：第二个下游项目踩到上述边界；要为跨作用域去重新增公开 API；审计语义要细化到"每次拒绝"。
