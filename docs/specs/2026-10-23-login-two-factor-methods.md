# 登录第二步支持多种验证方式

状态：已完成 · 风险档：高 · 关联：[#163](https://github.com/zengqinglei/leistd-net/pull/163)

## 1. 需求

### 问题与背景

下游 CRM（基于模板生成）的客户登录第二步有通行密钥、身份验证器、邮箱三种方式，做成三个并排标签页：默认停在通行密钥标签，要再点一次"使用通行密钥"；未登记的方式也显示为禁用标签；只要登记了邮箱，进入第二步就发一封验证码邮件，即使本人随后用的是身份验证器。用户希望模板给出一种通用的做法：开启多种方式时自动选默认方式，下方用一行小字提供"换一种方式"，与 Google、GitHub、Microsoft 的登录体验一致。

模板目前登录第二步只有身份验证器验证码和恢复码：输完密码直接进入 6 位码输入，输满自动提交，下方一行"改用恢复码"。邮箱验证码只用于注册、找回密码与改邮箱，不能作为第二步。

主流做法（2026-10 调研）：

| 产品 | 默认方式 | 切换入口 |
| --- | --- | --- |
| GitHub | 本人在设置里指定首选方式；未指定时按 安全密钥 > GitHub Mobile > TOTP > SMS | 下方链接列出其他方式，恢复码在最后 |
| Microsoft Entra | 系统首选（默认开启）：在已登记的方式里取最安全的，优先于本人设的默认值 | Sign in another way |
| Google | 按账号情况直接给出默认方式 | Try another way 打开方式列表 |

共同点：直接进入默认方式，不先让人选；下方一个低调的"换一种方式"；恢复码不作默认；默认由"首选设置 + 系统安全排序"决定。NIST SP 800-63B-4 不把邮箱当作带外认证方式（能进邮箱往往只凭一个密码），所以邮箱只作补充，不满足"必须启用两步验证"的组织要求。

### 目标

1. 已启用的本人可以把邮箱验证码作为第二步方式之一；可以与身份验证器并存，也可以单独使用。
2. 登录第二步直接进入默认方式，无需再点；默认方式按本人首选、再按系统排序决定。
3. 下方提示按备选数量给出：只有一种备选时直接写明，两种以上时只给"换一种验证方式"并展开列表。
4. 个人设置里能看到已开启的方式，能指定首选方式。

### 非目标

- 通行密钥（Passkey）：模板没有 WebAuthn，本次不加；方式列表与排序为它留位置。
- 确认身份对话框（敏感操作前的再认证）改用邮箱验证码：仍是口令或身份验证器二选一，另立变更。
- 短信、推送等其他渠道。
- 下游 CRM 的改造：由 CRM 按本规格自行对齐。

### 已确认的决策

| 决策 | 结论 | 确认 |
| --- | --- | --- |
| 邮箱能否满足"必须启用两步验证" | 不能；只有身份验证器满足 | 用户，2026-10-23 |
| 邮箱作第二步是否要组织开关 | 要，租户设置 `Security.AllowEmailTwoFactor`，默认关闭 | 用户按建议确认，2026-10-23 |
| 默认方式 | 本人首选（仍可用时）> 身份验证器 > 邮箱；恢复码永不作默认 | 同上 |
| 切换入口 | 一种备选直接写明；两种以上折叠为"换一种验证方式"列表 | 同上 |
| 不做"记住上次用的方式" | 与首选设置会互相打架，GitHub 同样只看首选 | 同上 |

### 功能要求与验收标准

**默认方式与切换**

- AC1：Given 本人只开了身份验证器，When 输完密码，Then 直接显示 6 位码输入并聚焦，下方只有"无法使用身份验证器？改用恢复码"。（前端 spec，现有行为保持）
- AC2：Given 本人开了身份验证器和邮箱、未设首选，When 输完密码，Then 默认身份验证器，下方是"换一种验证方式"，展开后依次是"邮箱验证码（发送到 j***@example.com）""恢复码"。（前端 spec）
- AC3：Given 同上但首选为邮箱，When 输完密码，Then 默认邮箱方式，自动发出验证码并显示打码后的地址与重发倒计时，不需要再点。（前端 spec + 集成测试）
- AC4：Given 首选为邮箱，但邮箱已改为未验证或组织关闭了邮箱方式，When 输完密码，Then 回落到身份验证器；没有其他方式时见 AC9。（集成测试）
- AC5：Given 默认是身份验证器，When 进入第二步，Then 不发送任何邮件；切到邮箱方式时才发送。（集成测试）
- AC6：Given 外部登录（GitHub 等）之后需要第二步，Then 行为与口令登录相同。（前端 spec）

**邮箱验证码第二步**

- AC7：邮箱验证码只对签发它的那一次第二步有效：换一次第二步、凭注册或找回密码的码都不通过。（集成测试）
- AC8：输错计入该次第二步的尝试次数，也计入账号的登录失败次数与锁定，与身份验证器一致；发送受现有发送间隔限制。（集成测试）
- AC9：Given 组织关闭了邮箱方式（或邮箱变为未验证），When 只开了邮箱方式的本人登录，Then 不再要求第二步，个人设置显示该方式"当前不可用"及原因。（集成测试 + 前端 spec）

**设置与组织要求**

- AC10：Given 组织允许邮箱方式且本人邮箱已验证，When 在个人设置开启邮箱验证码，Then 先确认身份，再输入发到邮箱的码完成开启，并收到安全提醒与操作记录。（集成测试 + 前端 spec）
- AC11：Given 组织要求启用两步验证，When 本人只开了邮箱方式，Then 会话仍受限，须设置身份验证器。（集成测试）
- AC12：Given 两种方式都能用，Then 设置页在默认方式的标题旁标"默认"、另一种给"设为默认"；停用首选方式后首选回到系统排序。（集成测试 + 前端 spec）
- AC13：没有 Email 能力的生成场景不出现邮箱方式、组织开关与相关文案；默认行为与 AC1 一致。（生成矩阵）
- AC14：Mock 与真实后端行为一致（AC1–AC12 中的界面路径），演示站可走通。（Mock spec + 人工验收）

### 非功能要求

- 不在 URL、日志与存储里出现邮箱原文以外的新增敏感信息；打码规则用 `TextRedactor.RedactEmail`。
- 第一步不产生发信副作用；邮件只在本人需要邮箱方式时发送。

## 2. 方案

### 现状事实

- 第二步挑战：`template/backend/src/CompanyName.ProjectName.Application/Auth/TwoFactor/TwoFactorChallengeStore.cs`，5 分钟、5 次，输错同时计入账号失败次数。
- 第二步校验：`AuthAppService.CompleteTwoFactorLoginAsync`，入参 `TwoFactorLoginInputDto` 为验证码与恢复码二选一。
- 是否需要第二步：`SessionIssuer.StartAsync` 看 `user.TwoFactorEnabled`（即存在身份验证器凭据）。组织要求判定：`UserSessionValidator` 同样看 `TwoFactorEnabled`。
- 邮箱验证码：`EmailChallengeStore` 按用途（注册、改邮箱、找回密码）签发与消费，带发送间隔与尝试次数。
- 前端第二步：`template/frontend/src/app/features/account/components/two-factor-challenge/`；外部登录经 `external-auth-callback` 以路由状态把 `twoFactorToken` 交给登录页。
- 迁移：模板 1.0.0（2026-10-21）发布后基线迁移未再改过，下游已有库。

### 设计

**领域**

- `User` 新增"邮箱作第二步已开启"标志与首选方式（可空）。身份验证器仍由 `TwoFactorCredential` 表示，它是唯一满足组织要求的方式。
- 方式枚举：身份验证器、邮箱、恢复码（恢复码只随身份验证器存在，只作备选）；留出通行密钥的位置。
- 可用方式 = 身份验证器（已启用）+ 邮箱（已开启 且 邮箱已验证 且 组织允许 且 发信可用）。需要第二步 ⇔ 可用方式（不含恢复码）非空。
- 默认方式：首选仍可用就取首选，否则按 身份验证器 > 邮箱。

**接口**

- 第一步输出 `SessionLoginOutputDto` 增加可用方式、默认方式与打码邮箱；外部登录完成走同一个 DTO，前端经路由状态一起带过去。
- 新增匿名端点 `POST /api/v1/auth/two-factor/email-code`（入参：第二步凭据），在 `EmailChallengeStore` 增加"登录第二步"用途，码绑定该次挑战与用户安全版本；受发送间隔限制。
- `TwoFactorLoginInputDto` 增加 `EmailCode`，三者恰好给一个。
- 个人设置：两步验证状态输出增加各方式的开启与可用情况、首选方式；新增开启（发码 → 确认）/停用邮箱方式与设置首选方式的端点。开启与停用要求近期认证，记操作记录并发安全提醒。
- 租户设置 `Security.AllowEmailTwoFactor`（布尔，默认 false，对客户端可见），只在 Email 能力下注册。

**前端**

- 第二步组件按默认方式初始化；邮箱方式进入时自动发码，显示打码地址与重发倒计时（复用 `resend-countdown`）。
- 下方提示：备选只有一种时显示具体说明；两种以上时显示"换一种验证方式"，展开为带图标与说明的列表，恢复码在最后。
- 个人设置两步验证区改为方式列表：身份验证器（沿用现有启用、换绑、恢复码流程）、邮箱验证码（开关）、首选标记与"设为首选"（开了两种及以上才出现）。
- Mock 同步实现以上接口。

**迁移**

新增一个增量迁移给用户表加两列，不改基线：下游项目已经按 1.x 基线建库，改基线不会给已有库补列。

### 备选与取舍

- **第一步就自动发邮件**：省一次请求，但默认是身份验证器时也会发信（CRM 现状），外部登录路径还得同样处理。改为进入邮箱方式时才发。
- **标签页并排列出全部方式**（CRM 现状）：默认停在一个需要再点的方式上，未登记的方式也占位。改为只显示默认方式 + 折叠的备选列表。
- **组织开关关闭时继续认可已开启的邮箱方式**：开关就失去意义；关闭时只开了邮箱的人回到单步登录，由管理员有意决定，设置页写明原因。

### 兼容与回滚

- 接口只增字段与端点，旧客户端忽略新字段仍可用身份验证器与恢复码。
- 迁移只加可空或有默认值的列；回滚为删除这两列的 Down 迁移。
- 组织开关默认关闭：升级后行为与现在一致，直到管理员打开。

## 4. 结果

### 实际交付

与本规格同一变更还交付了个人设置"新密码"规则提示的调整（低风险，不单写规格）：标签下的长说明换成输入框下方的四格长度进度条，界面不显示文字（只给读屏），规则在不满足时由校验错误说明；注册、找回密码、修改与设置密码、管理员重置用户密码五处共用 `core/components/password-length-meter`（组件以 `hostDirectives` 注册为字段描述）。

登录第二步按 §2 实现：领域 `TwoFactorMethod`、`User` 的邮箱方式与首选；`TwoFactorMethodResolver` 统一判定；第一步输出可用方式与默认方式；`POST /api/v1/auth/two-factor/email-code` 发码；个人设置的邮箱方式开关与首选；租户设置 `Security.AllowEmailTwoFactor`；增量迁移 `AddTwoFactorMethods`；前端第二步组件、邮箱设置组件、Mock、中英词条、操作记录与安全提醒。

### 与计划的偏差及原因

- 设置页没有把身份验证器一节改成方式列表，而是新增独立的"邮箱验证码"小节；身份验证器一节原样保留，改动面更小。首选不单独成段：两种方式都能用时，默认方式的标题旁标"默认"，另一种在自己的操作里给"设为默认"（用户评审时提出，起初做成独立的"登录时先使用"单选）。
- 用户评审时还比较过登录页租户的六种展示方式（只读字段、标题下一行加浮层、右上角按钮、两步式、移到登录按钮下方等），最终保持现状，本变更不改登录页的租户。
- 找回口令的 `PasswordResetTarget/Proof` 更名为通用的 `EmailCodeRecipient/EmailCodeProof`，邮件正文版式抽成 `VerificationCodeMail` 共用：两步验证的两种用途同样绑定账号与安全版本。
- 邮箱一节的中文用词由"开启/关闭"统一为"启用/停用"，与身份验证器一节一致。
- 审查（Codex，两轮）后补：发信失败不退出第二步、Mock 身份验证器分支要求已启用、Mock 启用确认码校验到期、登录码邮件改为中性文案、邮箱输错跨挑战计入锁定与重发不清零次数的集成测试。
