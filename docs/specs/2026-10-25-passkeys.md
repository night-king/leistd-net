# 通行密钥（WebAuthn / Passkey）

状态：进行中 · 风险档：高 · 前序：[登录第二步支持多种验证方式](2026-10-23-login-two-factor-methods.md)、[邮箱不是独立因子](2026-10-25-two-factor-email-factor-scenarios.md) · 参考：下游 identity main `7aa63af6`（`docs/modules/identity/multi-factor-authentication.md`）

## 1. 需求

### 问题与背景

模板现在的第二步方式有三种：身份验证器（TOTP）、邮箱验证码、恢复码。上一轮确认"邮箱不是独立因子"之后，第二步只开了邮箱的账号不能再自助找回口令；独立因子也只有身份验证器一种，手机丢了就只剩恢复码或管理员重置。下游 identity 已经落地了通行密钥（WebAuthn）。用户要求以它为参照，把通行密钥做进模板，同时覆盖后端、登录、个人设置与系统设置，符合框架规范、开发规范和终局原则。

业界做法（2026-10）：

| 产品 | 通行密钥的用法 | 恢复码 |
| --- | --- | --- |
| Google | 默认的免口令登录方式，登录时不再要求两步验证 | 账号级备用码，与具体方式无关 |
| GitHub | 免口令登录（满足两步验证要求），也可作第二步的安全密钥 | 开启两步验证即发放，账号级 |
| Microsoft | 免口令、抗钓鱼的首选方式；Entra 视作满足 MFA | 账号级恢复码 |

共同点有三条：
- 通行密钥要求用户验证（生物识别或 PIN），一次就具备"持有 + 本人"两个因素，所以作为第一步可以直接完成登录。
- 恢复码挂在账号上，开启第一个强因子时发放。
- 删除最后一个强因子时，恢复码随之作废。

### 选型：官方机制与第三方库

ASP.NET Core 10 Identity 内置了通行密钥，但官方文档写明了两条限制："Scoped to ASP.NET Core Identity"（只用于 Identity 自己的认证场景）和 "No built-in 2FA support: Passkeys are treated as a primary authentication factor"（不支持作为第二步）。它的默认实现还要经 `UserManager<TUser>` 解析用户。模板用的是自有 User 聚合，没有 ASP.NET Core Identity，所以这套内置能力用不上。同一份文档对需要完整 WebAuthn 的场景推荐 fido2-net-lib，identity 用的也是它。

本方案采用：
- **后端** `Fido2`（Fido2NetLib）4.3.1，当前最新稳定版（5.0 仍是预览版）。只引用 `Fido2` 与 `Fido2.Models`，不引入 `Fido2.AspNet`。
- **前端**不引第三方库。手写一个不到百行的 base64url 与 `navigator.credentials` 封装，与 identity 的做法一致。

### 目标

1. 本人可以登记多把通行密钥，管理每一把：重命名、删除，查看登记时间、最近使用时间与备份状态。
2. 登录时可以直接用通行密钥完成，免口令、免用户名：登录页提供"用通行密钥登录"按钮，用户名框支持浏览器自动填充里的条件式通行密钥。
3. 口令登录或外部登录之后，通行密钥也可以作为第二步方式。它是独立因子，排在默认方式顺序的第一位。
4. 通行密钥满足组织的"要求两步验证"。
5. 确认身份对话框可以用通行密钥确认。
6. 恢复码改为账号级：开启第一个独立因子（身份验证器或通行密钥）时发放，最后一个独立因子去掉时作废。
7. 管理员重置两步验证、部署命令重置、统计、操作记录与安全提醒一并覆盖通行密钥。

### 非目标

- 证明（attestation）校验与 FIDO MDS：取 `none`，不验认证器型号。只有政企场景需要，留作宿主扩展点（见 §2）。
- 跨域名或多个 RP ID：一个部署只有一个 RP ID。多租户按子域名部署时，RP ID 取父域。
- 下游 CRM 的改造：由 CRM 按本规格自行对齐。

### 功能要求与验收标准

**登记与管理**（个人设置的安全区）

- AC1：Given 部署已配置 RP，且会话近期认证过，When 本人添加通行密钥，Then 浏览器弹出创建界面，完成后列表多一行，默认名称取自设备与浏览器，并发出安全提醒、写入操作记录。会话不够新时先确认身份；确认之后要本人再点一次才继续创建，因为浏览器要求用户手势。（集成测试 + 前端 spec）
- AC2：登记时排除本人已有的凭据，同一认证器重复登记时提示"已添加过"。凭据 Id 全局唯一，被别人占用时拒绝。（集成测试）
- AC3：可以重命名与删除；删除要求近期认证。组织要求两步验证、且它是最后一个独立因子时，拒绝删除。删除最后一个独立因子时恢复码作废，指向它的首选回到系统顺序，并撤销本人的其他会话。（集成测试）
- AC4：部署没配 RP、浏览器不支持或不在安全上下文时，添加按钮不可用，并说明原因。（前端 spec）

**登录**

- AC5：Given 本人有可发现的通行密钥，When 在登录页点"用通行密钥登录"，或在用户名框里从自动填充选中通行密钥，Then 直接签发会话，不再要求第二步，也不受"口令经邮件找回"标记的影响，并记录登录成功。（集成测试 + 前端 spec）
- AC6：Given 口令登录之后需要第二步、本人有通行密钥，Then 默认方式是通行密钥（本人另设了首选时以首选为准）。界面点一下即发起验证，不自动弹出；也可以换别的方式。（集成测试 + 前端 spec）
- AC7：断言失败（签名不对、凭据不属于本人、计数器回退、挑战过期或被替换）不签发会话。失败计入账号的登录失败与锁定，与验证码一致。锁定或停用的账号不能用通行密钥登录。（集成测试）
- AC8：通行密钥满足组织要求，只有通行密钥的人会话不受限。受限会话可以登记通行密钥来解除限制。（集成测试）

**确认身份**

- AC9：确认身份对话框给出本人具备的方式：口令、身份验证器验证码、通行密钥。选通行密钥时点一下发起验证，通过后重放原请求。所有接受确认身份的入口都接受通行密钥证明。（集成测试 + 前端 spec）

**恢复码**

- AC10：开启第一个独立因子时发放恢复码；只有通行密钥的人也有恢复码，可以重新生成。恢复码在第二步与确认身份中的用法不变。去掉最后一个独立因子时恢复码作废。已有数据迁移后，身份验证器用户的恢复码保持不变、仍然可用。（集成测试 + 迁移测试）

**管理与运维**

- AC11：管理员重置两步验证、部署命令 `--reset-two-factor` 同时删除通行密钥；用户列表的"已启用两步验证"、统计里的"管理员未启用两步验证"都按"有独立因子"计算。（集成测试）
- AC12：没有 Email 或 ExternalLogin 的生成场景照常可用；Resource 形态不生成任何通行密钥代码。（生成矩阵）
- AC13：Mock 支持登记、登录、第二步与确认身份的界面路径，演示站可以走通，用浏览器真实的平台认证器或 Chrome 虚拟认证器。（Mock spec + 人工验收）

### 非功能要求

- 挑战存放在分布式缓存，5 分钟有效，按注入时钟判定到期。注册挑战绑定会话与安全版本；登录挑战绑定第二步凭据，或绑定匿名登录的那一次请求。
- 用户验证 `Required`，证明 `None`，可发现凭据 `Preferred`。
- WebAuthn 请求与响应按 Fido2 自己的 JSON 规则序列化，不走全局 JSON 选项：COSE 算法必须保持数字，`public-key` 等字面量不能被全局枚举转换器改写。
- 凭据 Id、公钥、AAGUID、传输方式、备份标志存明文列；公钥不是秘密，凭据 Id 建唯一索引。

## 2. 方案

### 领域与持久化

- `TwoFactorMethod.Passkey = 4`，`IsIndependent` 为真。默认方式的系统顺序为：通行密钥 → 身份验证器 → 邮箱，恢复码永不作默认。
- 新聚合 `UserPasskey`（`Domain/Auth/Entities`），形态参照 `ExternalLoginConnection`：`DeletionAuditedEntity<Guid>`、`IAggregateRoot`、`IMultiTenant`。字段如下：
  - `UserId`、`CredentialId`（byte[]，未删除行唯一）、`PublicKey`、`SignCount`、`UserHandle`、`Aaguid`、`Transports`、`IsBackupEligible`、`IsBackedUp`；
  - `Name`（最长 128），`LastUsedTime`。
- `User` 的变化：
  - 恢复码从 `TwoFactorCredential` 移到 User 上的值对象 `RecoveryCodeSet`（摘要与剩余数），迁移时原样搬过去；
  - 新增 `HasIndependentFactor`（身份验证器，或至少一把通行密钥），以及更新它的领域方法。各处"满足组织要求""能找回口令""已启用两步验证"的判定统一改读这个属性。
- 增量迁移：建 `UserPasskeys` 表，搬恢复码列。

### 基础设施

- 端口 `IPasskeyVerifier` 放 Domain 或 Application，适配器 `Fido2PasskeyVerifier` 放 Infrastructure，与口令哈希同一模式。Fido2 的类型不外露，以后换库只换适配器。
- 宿主级 Options `Passkeys`，含 `RelyingPartyId`、`RelyingPartyName`、`Origins[]`，在启动期校验格式。
  - 没有配置时功能不可用：设置页说明原因，登录页不显示按钮。属于宿主的显式选择，按取舍原则 §5 第 4 条写进文档，不加门槛。
  - Development 档默认 `localhost`，Origins 为 `http://localhost:4200`。
  - compose 与 `.env.example` 加两个可选键。
- 证明校验留扩展点：Options 里放一个可选委托，默认不校验。

### 接口

| 用途 | 端点 | 说明 |
| --- | --- | --- |
| 登记 | `POST me/two-factor/passkeys/options` → `POST me/two-factor/passkeys` | 近期认证、凭据锁、仪式绑定会话与安全版本；首个独立因子时一并返回恢复码 |
| 管理 | `PUT me/two-factor/passkeys/{id}/name`、`DELETE me/two-factor/passkeys/{id}` | 删除要求近期认证 |
| 状态 | `GET me/two-factor` | 输出增加通行密钥列表与"不可用原因" |
| 第二步 | `POST auth/two-factor/passkey-options`（第二步凭据）→ `POST auth/two-factor` 的 `passkey` 字段 | "恰好一种"的判定把它计入 |
| 免口令 | `POST auth/passkey-login/options` → `POST auth/passkey-login` | 匿名；仪式 Id 由服务端签发；租户在发 options 时定案 |
| 确认身份 | `POST auth/me/reauthentication/passkey-options`，证明字段 `passkey` | `ReauthenticationProof` 增加一种 |

### 前端

- `core/webauthn/` 放 base64url 与 `create`/`get` 的封装、错误归类（取消、已存在、不支持）和默认设备名。确认身份对话框在 core 层，因此封装也放在 core。
- 登录页加"用通行密钥登录"按钮，并启用条件式 UI：用户名框 `autocomplete="username webauthn"`，进入页面时发起 `mediation: 'conditional'`。
- 第二步组件加通行密钥方式。
- 个人设置的安全区新增"通行密钥"一节，与身份验证器、邮箱一节并列，含列表、添加、重命名、删除、备份状态，以及"只有通行密钥时，提示再加一把或身份验证器"。
- 确认身份对话框加通行密钥方式。
- 系统设置页无改动：没有新的租户设置，RP 是部署配置。
- Mock 实现全部端点：登记时保存浏览器返回的凭据 Id；验证时只认已登记的 Id，不校验签名。

### 备选与取舍

- **ASP.NET Core Identity 内置通行密钥**：前提是采用 Identity 的用户模型与存储，而且不支持作为第二步。不采用，依据见 §1。
- **只做第二步**（identity 的做法）：通行密钥的主要价值在免口令登录，三家主流产品都把它当首选登录方式。只做第二步，以后还要加回来。按终局原则本次一起做。
- **凭据存进加密 blob**（identity 的做法）：查不了凭据 Id、建不了唯一索引，免口令登录需要按凭据 Id 定位用户。改为明文列，公钥本来就不是秘密。
- **新增模板参数**：会多出一个矩阵维度，收益很小。通行密钥只依赖本地身份，随 `LocalIdentity` 生成；部署可以不配 RP，功能自然关闭。

### 兼容与回滚

- 接口只新增字段与端点。第二步入参多了一种，原有三种的语义不变。
- 迁移新建一张表，并把恢复码搬到新列；Down 迁移搬回原处。
- 新增依赖 `Fido2`、`Fido2.Models` 4.3.1，在 `tech-stack.md` 写明收益、成本与风险，并经依赖审计。
