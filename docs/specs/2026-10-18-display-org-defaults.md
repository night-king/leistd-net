# 界面语言与时区：组织默认 + 个人覆盖

状态：已完成（PR #118）

> 在途计划（2026-10-18）。用户要求“按最佳实践终局决策，不考虑是否推翻之前的设计”。完成后按仓库惯例处理在途计划。

## 1. 背景

模板现在把 `Display.Language`、`Display.TimeZone` 定义为**仅用户级**，代码默认值为空，表示跟随浏览器（`SettingDefinitionProvider.cs:46-73`，2026-09-10 08e3235c）。当时的理由是：同一租户里语言不同的人很多，租户默认值会让一半人先看到不对的语言。

用户在测试中发现系统设置里没有语言配置，并给出对照：业务项目 CRM-V2 有系统级语言与时区设置。但 CRM 在宿主、租户、用户三级都默认 `en`、`Asia/Shanghai`，登录后有效值永不为空，浏览器语言从不生效。

两种做法各缺一块：

| | 缺口 |
|---|---|
| 仅用户级（模板现状） | 组织无法规定工作语言（例如日企要求全员日语，员工电脑却是英文系统，或者是共用终端）；服务端没有浏览器时（发给从未登录用户的邮件，或触发者不是收件人的通知）只能用触发请求的语言或 UTC |
| 三级都写死默认值（CRM） | 默认值永不为空，浏览器语言失效；中文浏览器登录后也被切成英文 |

“组织给默认、个人可覆盖”是常见的产品模式（各产品的适用范围不完全相同：Slack 的工作区默认语言主要影响邀请邮件，Salesforce 的组织默认用于新用户）。本方案结合模板既有契约作出决策：组织没设时跟随设备。

## 2. 决策

两项设置都改为**租户默认 + 个人覆盖**（`SettingScopes.All`），默认值为空，表示跟随浏览器。部署方可以用配置给所有租户一个基线。

### 2.1 解析链

- **浏览器**：个人值 → 组织值 → 部署基线 → 设备偏好 → 内置默认。
  - 语言的设备偏好沿用 `LanguageService.loadDeviceLang()`：先取未登录时显式选过的 `app_lang`，再匹配浏览器语言，最后是 `en`。不能把它简化成只看浏览器，否则会丢掉用户已有的设备选择。
  - 时区的设备偏好是浏览器时区。
- **服务端**：个人值 → 组织值 → 部署基线 → 触发请求的文化（时区回落 UTC）→ `en`。

前两段沿用框架现有的“用户 → 租户 → 代码默认值”。部署基线就是代码默认值，从配置读取，不改框架。

### 2.2 部署基线：沿用 Options 写法，不改框架

框架没有“宿主值传给租户”的层级（`EfCoreSettingStore.cs:191-201`）：宿主在系统设置里写的值只对宿主上下文生效，这和其他租户级设置一致。全部署统一默认值的需求，按注册开关、会话时限已有的写法处理：

- 新增 `DisplayDefaultsOptions { Language, TimeZone }`，绑定配置节 `DisplayDefaults`，两项都默认为空。
- `SettingDefinitionProvider` 注入该 Options，作为两项的 `defaultValue`。空串和空白视为“未配置”，归一为 null。
- 启动校验只校验非空值：Language 必须是支持的语言，TimeZone 必须是有效的 IANA 名，不合法则启动失败并给出明确信息。用纯值规则校验，不注入 `IUserTimeZoneProvider`，避免 Options → 时区服务 → 设置定义 → Options 的依赖环。另加一条零配置能正常启动的正向测试。
- **条件裁剪**：`Language` 属性及其校验只在 `IncludeLocalization` 下存在；`TimeZone` 在所有形态都有。
- **注册位置**：Options 的注册和绑定放在所有形态都会走的入口，资源服务形态也要有，不能复用只在 `LocalIdentity` 下的注册入口。资源服务形态的 `SettingDefinitionProvider` 分支当前没有构造参数，`Microsoft.Extensions.Options` 的 using 也带条件守卫，需要一起调整。
- **生命周期**：定义管理器在进程内只构建一次，所以部署基线是启动期基线，修改后要重启各实例并保持配置一致。文档写明这一点，不暗示配置热重载会生效。
- `appsettings.json` 写出这个节，值为空，并加一行注释说明含义。

不做框架的“全局层”：它会改变所有租户级设置的继承语义（例如宿主关闭自助注册会连带所有租户），代价和风险都超出本需求。多租户下，“系统设置”编辑的是当前组织；全部署统一的默认值由部署配置提供。如果以后产品要求宿主在界面上动态控制所有组织，那是新的需求，不能把当前组织设置说成这项能力。

### 2.3 后端

- 两项设置改为 `SettingScopes.All`，`defaultValue` 取自部署基线。注释改为新的理由和解析链。
- 新增分组子权限 `App.Settings.Display`（宿主与租户），登记进 `SettingGroupPermissions`；权限的显示名与词条加中英两份。
- 系统设置面板的顺序：Display 作为“显示”面板放在第一位，因为定义顺序决定面板顺序，个人偏好里它也排在第一。同步更新 `SettingsContractTests` 的期望。
- 服务端渲染：
  - 语言：`EmailChangedEventHandler`、`NotificationSecurityAlertPublisher` 现在用 `GetOrNullForUserAsync`，已经是“用户 → 租户 → 默认”，组织值会自然生效，只改注释。
  - 时区：锁定提醒里的 `{Until}` 改为按收件人的有效时区输出，并带上时区标识；回落到 UTC 时同样带标识，不再写死“(UTC)”。
    - `IUserTimeZoneProvider` 增加 `GetForUserAsync(userId)`：沿用用户 → 租户 → 默认 → UTC 的回落，读的是当前租户环境，不会凭 userId 跨租户查找（注释写明）。
    - 同一改动里一起更新三处文案：`Resources/en.json:161` 的 `{Until} (UTC)`、`Resources/zh-CN.json:161` 的 `{Until}（UTC）`，以及单语言形态的内置英文。
    - `NotificationSecurityAlertPublisher` 的本地化分支（`#if`）和单语言分支（`#else`，目前是 static 方法）都要接上按收件人解析时区。
- 单语言形态（`!IncludeLocalization`）没有语言设置，只调整时区。资源服务形态的这两项定义不在 `LocalIdentity` 条件块里，同样适用。

### 2.4 前端

- 系统设置显示“显示”面板（语言、时区）。图标和面板说明加中英文案。
- 占位文案按当前的有效值区分，和 `SettingContextService.valueOf()`（个人 ?? 组织 ?? 默认）保持一致：

  | 页面 | 本层未设时的情形 | 占位 |
  |---|---|---|
  | 个人 | 组织有值 | 跟随组织 · 组织值 |
  | 个人 | 组织未设、部署基线有值 | 跟随组织 · 部署基线值 |
  | 个人 | 三层都空 | 跟随系统 · 当前设备检测值 |
  | 系统 | 部署基线有值 | 部署默认 · 基线值 |
  | 系统 | 部署基线为空 | 跟随系统（不显示管理员自己的设备检测值，避免误导） |

  本层有值时直接显示该值。
- 语言切换器写入用户层后，经 `SessionContextService.refreshSettings()` 刷新，和 `SettingSection.write()` 的做法一致，不单独调用下层的 load。这修复了已有的不一致（写入后上下文不更新）。保留现有的失败提示契约。切换器本身不加“跟随组织”项，恢复入口在偏好页的“恢复默认”。
- 生效时机：组织修改后，其他在线用户在下一次会话设置刷新或重新登录时生效。不新增广播或轮询。
- 个人偏好页的说明文案（`settings/*.json:59`、`personal-settings.ts:124`）改为“留空即跟随组织设置；组织和部署都未设置时跟随系统”。

- PUT current-tenant 增加层级校验：设置不允许租户层时返回 400（与真实后端一致），避免 Mock 放行掩盖差异；同步修正现有 spec。
- 演示角色给 admin 补授新子权限。

## 3. 不做

- 登录前按租户默认显示语言：拿设置需要登录，登录页仍按设备或浏览器语言显示。
- 框架层面的宿主到租户继承：见 §2.2。

## 4. 测试

- **后端集成测试**：
  - 租户值让用户的未设值生效，用户值优先；部署基线作为默认，能被继承、覆盖，清除后回落；
  - 宿主在系统页写的 Display 值只影响宿主上下文，租户读不到；
  - 邮件、提醒按收件人的租户语言渲染；
  - 锁定提醒的时间和时区标识一致，覆盖：个人时区优先、组织回落、部署基线、最终 UTC，本地化开和关两种。输入里让当前用户与收件人不同，证明走的是按目标用户解析的路径；
  - `GetForUserAsync` 的单测不能只靠现有 `FixedSettingProvider`（它把按用户读取直接委托给当前值），要能区分出目标用户；
  - 零配置能启动；非法的非空基线导致启动失败；
  - 权限：普通用户没有管理权限，仍能读两项的有效值、写个人覆盖；管理组织值需要 `App.Settings` 和 Display 子权限，否则 403。
- **前端**：
  - 系统页出现显示面板；占位按 §2.4 表格的五种情形；
  - 切换器：写入成功后上下文已刷新；写入失败、写入成功但刷新失败两种情况；退出或换主体后恢复设备偏好；
  - Mock 层级校验。
- **形态条件**：资源服务、无前端的资源服务、单语言、无 Email 等形态都不依赖新增的本地身份能力；新增的整文件条件源码和测试要同步登记排除。
- **验证范围**：
  - 模板矩阵：identity-all-features、**identity-notifications**（通知开、本地化关）、identity-capabilities-01、standalone-capabilities-02、resource、standalone；
  - 前端四形态；全部有效形态生成；
  - 演示站点端到端：组织设语言后用户随之切换；个人覆盖优先；清除个人或组织覆盖后回落正确。
