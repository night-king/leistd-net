## 1. 调研结论

只列会改变我们做法的结论。来源编号对应 research.md。

1. **验证闭环比规格文档重要。**
   - 给代理一个能自己判定通过或失败的检查，并要求它出示证据【共识 CC、KB、GHC】。
   - 我们的 `verify.ps1`、风险档和定向证据已经符合，这一部分不动。
2. **计划按风险分档。**
   - 业界经验法则是"一句话能描述的 diff 就不写计划"【CC】。
   - Kiro 和 spec-kit 都把 bug 修复单独做成轻量流程，只写"当前行为 / 期望行为 / 不变行为"【KI、SK】。
   - 规格有"写完即弃"、"随功能维护"、"规格即源码"三个层次，多数工具目前停在第一层；规格方法也可能制造大量需要人审的 markdown【MF1】。保留规格是本仓库的取舍，不以"业界都丢弃"作反证。
   - **结论：不引入 spec-kit/Kiro 式的强制三件套。**
3. **验收标准要结构化、能改写成测试**【共识】，用 Given/When/Then 还是 EARS 都可以，选一种即可。需求由人拍板；AI 负责访谈，列出待澄清项【CC、SKd】。
4. **AI 是放大器**【DORA 2024/2025】：吞吐量上去了，稳定性受冲击，要靠小批量、强版本控制和快速 CI 对冲。这支撑刚完成的 CI 提效，也要求生产侧有可回滚、不可变的产物【12F、DCD】。
5. **运维场景**【共识 OWASP、MCP】：
   - 最小权限，授权由下游系统强制执行，不交给模型判断；
   - 高影响操作要人审批，并保留审计记录。
   - 实验显示 LLM 目前还不能稳定地自主定位线上根因【CH】，所以 AI 的角色是汇总、起草、提出下一步。
   - 数据修正没有权威规范。最接近的一手模式是 Anthropic 的 plan-validate-execute【SBP】，与用户全局约定一致，适合写成**低自由度的固定流程**，步骤顺序见 §5.2 B-b：先备好恢复方案并预演，再确认，最后执行。
6. **复盘**：先止损再找根因，复盘有事先定义的触发条件【SRE】。回写给代理的知识要做减法：只在代理重复犯错时加规则，并定期修剪【共识 CU、MF2、CC】。
7. **文档分层**【共识】：
   - 常驻层（AGENTS.md / CLAUDE.md）短，只放指针；
   - 按需层是 Skill，SKILL.md 控制在 500 行以内，引用文件只往下一层；
   - 决策用 ADR，只追加，失效时标 superseded；
   - 计划和需求说明是一次性产物。

## 3. 交付流程与文档沉淀

### 3.1 总原则：现行规则和变更依据分开存

AI 时代"效率至上"包括两层意思：
- **写的成本低**：文档由 AI 在对话中边做边写，人只确认关键结论。
- **读的成本低**：AI 默认只读取现行规则；需要追溯"为什么"时，再按需读取依据。

两类文档的区别：

| 类别 | 回答什么 | AI 何时读取 | 生命周期 |
| --- | --- | --- | --- |
| **常驻文档（现行规则）** | 系统现在是什么样、应该怎么做 | 默认读取，按索引路由 | 随代码同步修改，始终只描述当前状态 |
| **规格文档（依据）** | 某次为什么改、怎么定的、实际交付了什么 | 只在需要追溯时读取 | 一次一份，**保留，不删除，不移动** |

两类分开以后，规格文档可以放心保留，不会污染 AI 的默认上下文。这样也补上了"想查看相关内容却找不到依据"这个缺口。

框架仓库原来规定计划完成即删，这条改为保留，原因是框架的取舍同样需要可追溯的依据。

### 3.2 规格文档（`docs/specs/`）：需求、方案、计划合一

参照 superpowers：
- 它按任务规模分为"直接做 / 对话内 / 写设计文档"三档；
- 设计文档和计划都提交进仓库并长期保留（`docs/superpowers/specs/`、`docs/superpowers/plans/`）。

我们在此基础上再减一层：**一次变更只写一份文件**，需求、方案、计划、结果是这份文件里的四节，按风险档逐级出现。

**位置**：两层统一为 `docs/specs/YYYY-MM-DD-<topic>.md`。需要配图、报告等附件时，放进同名目录 `docs/specs/YYYY-MM-DD-<topic>/`。

**固定结构**：一级章节固定，便于 AI 检索和对比；章节内容不套模板。

```markdown
# <主题>

状态：进行中 | 已完成 | 已废弃（被 <文件> 取代） · 风险档：中 | 高 · 关联：<PR/MR 链接>

## 1. 需求        ← 取 PRD 的精简要素；有外部 PRD 时链接原文，只提炼下面几项
问题与背景；目标用户与使用场景；目标与非目标；成功指标（能度量时才写）；
功能要求 → 验收标准（Given/When/Then，每条注明由哪个自动化测试覆盖，或标"人工验收"）；
非功能要求（性能、安全、兼容，有约束时才写）；待定问题与已确认的决策（谁、何时确认）

## 2. 方案        ← 高档必写
现状事实（附路径证据）；设计（模型、接口、流程、迁移，可用 mermaid）；
备选与取舍（只列会改变边界的）；兼容与回滚

## 3. 计划        ← 高档，或需要跨会话、跨多个 PR 时写
任务（每项写产物与验证方式）；不做的事

## 4. 结果        ← 完成时填写
实际交付（PR 列表）；与计划的偏差及原因；验收记录（环境、版本、结论、验收人）；
遗留项；已上收到哪些常驻文档
```

**按风险档写多少**：

| 风险档 | 规格文档 | 其他 |
| --- | --- | --- |
| 低：小修复、措辞、单点调整 | 不写 | 缺陷按"当前行为 / 期望行为 / 不应改变的行为"三段写在 PR/MR 描述里 |
| 中：一般需求、一般缺陷修复、重构 | 写 §1 需求、§4 结果；方案用一段话写在 §1 末尾 | 计划只放在会话里 |
| 高：公共 API 或破坏性变更、数据模型与迁移、权限、跨层或跨服务、发布流程 | 写全 §1–§4 | 不可逆的决策同时上收到常驻文档 |

**粒度**：计划只写到"任务 + 产物 + 验证"这一层。逐步骤的执行台账（比如 superpowers 的 checkbox 步骤、子代理进度）属于会话执行状态，放在 `.tmp/` 或 `.superpowers/`，不提交。

**生命周期**：
1. **创建**：需求确认（S1）时创建。用户请求或会话中已经明确的需求和授权直接写入 §1 并视为已确认，只有真正待澄清的事项或新增的关键决定才停下来询问。最迟随第一个实施 PR 提交；何时提交服从用户指示。
2. **更新**：决策变化时直接改原文，历史由 Git 保留；不另写修订记录。
3. **完成**：在完成变更的那个 PR 里一起做三件事：
   - 填写 §4 结果；
   - 状态改为"已完成"；
   - 把仍然成立的规则上收到常驻文档。
4. **之后**：不删除，不移动。状态行就是唯一标记。目录按日期自然排序，不另建索引。

**按档出现，不占位**：四节随风险档出现，没有内容的章节和字段（比如低风险变更的验收人）不写占位。

**例外：紧急止损和热修**。先按 `delivery.md` 的热修通道止损并修复，不先写规格；在事件收尾或修复 PR 合入时补一份简短规格，只写 §1 现象与原因和 §4 结果；需要复盘时，按 `operations/incidents/` 的规定另写。

**和 superpowers 共存**：superpowers 规定"用户偏好优先于默认路径"，但它的 brainstorming 和 writing-plans 默认会分别产出规格和计划两份文件。AGENTS.md 写明以下三点即可，不修改插件，也不新建适配层：
- 规格写到 `docs/specs/YYYY-MM-DD-<topic>.md`；
- 计划写进同一个文件的 §3，不另建文件；
- 何时提交服从用户指示。

### 3.3 常驻文档：何时必须更新

**业务项目**

| 常驻文档 | 内容 |
| --- | --- |
| `docs/requirements/{topic}.md` | 按业务主题记录当前规则，沿用现有约定 |
| `docs/modules/{module}/README.md` | 模块的技术边界与契约 |
| `docs/project/` | 项目规则与决策 |

改动触及下列任一项时，在同一个 PR 里更新对应的常驻文档。这 6 项是客观条件，可以对照 diff 逐项核对：

1. 业务规则或校验：取值范围、计算口径、唯一性、额度、时限；
2. 状态，以及状态之间的流转条件；
3. 权限：权限点、角色可见范围、租户隔离；
4. 对外契约的业务含义：错误码含义、事件、导入导出格式，以及会改变调用方行为的接口规则；字段本身以接口定义和代码为准；
5. 数据含义：新增字段，或现有字段的业务含义改变；
6. 用户可见的流程：步骤、入口、通知（单个界面控件不算）。对应主题还没有常驻文档时，触及上述条件就新建一份。

**框架仓库**

| 常驻文档 | 内容 |
| --- | --- |
| `framework/docs/` | 公共契约 |
| `docs/architecture/`、`docs/framework/`、`docs/template/` | 维护规范 |
| `template/docs/` | 生成项目的规范 |

触发条件已经是客观的：改了公共 API、注册方式、运行时语义，或者改了维护流程，就更新对应的常驻文档。

常驻文档只写意图和规则，不复述代码里一眼能看出的内容。规则尽量指向对应的测试。

交付汇报固定包括两项：
- 规格文档的状态；
- 哪些常驻文档已经同步。

6 项条件是核对提示，汇报时只写有变化的项，不逐条列"无变化"。

审查时发现漏了，按缺陷处理。不加脚本闸门，因为这属于流程合规，不是产品正确性。

### 3.4 提交规则

| 文档 | 何时提交 |
| --- | --- |
| 规格文档 | §1 确认后就可以单独提交，最迟随第一个实施 PR 提交。§4 和状态随完成变更的那个 PR 提交 |
| 常驻文档 | 和对应的代码改动放在同一个 PR |
| 缺陷三段式、验收截图 | 写在 PR/MR 描述或附件里，不落文件 |
| 会话执行状态（`.tmp/`、`.superpowers/`、子代理台账） | 不提交，已被 gitignore |

交付前，`git status` 里不应再有未跟踪的 `docs/specs/` 或常驻文档；如果有，要么纳入提交，要么在汇报里说明原因。何时提交仍以用户指示为准。

### 3.5 阶段与产物

| 阶段 | 产物 | 位置 |
| --- | --- | --- |
| S1 需求确认 | 规格文档 §1 | `docs/specs/` |
| S2 需求沉淀 | 先写进规格 §1；常驻规则随实现它的 PR 一起更新，不提前写尚未实现的行为 | B：`requirements/`、`modules/`；F：`framework/docs/`、`docs/*` |
| S3 方案与计划 | 规格文档 §2、§3 | `docs/specs/` |
| S4 实施与本地闭环 | 定向证据 | PR 描述 |
| S5 提交、CI、产物 | 不可变产物（NuGet 版本 / 镜像 SHA） | 包源、镜像仓库 |
| S6 测试环境验收 | 规格文档 §4 验收记录；截图放附件 | `docs/specs/`、MR 附件 |
| S7 生产发布 | 发布说明（自动聚合，AI 改写，人审） | Release 正文 |
| S8 上线后 | 事件与复盘、Runbook | B：`docs/operations/` |

运维场景（查询、排查、数据修正）不走规格文档，按 `operations.md` 的固定流程执行；热修不以前置规格阻塞，事后按 §3.2 补记。运维记录写在 `docs/operations/`。如果排查后要改代码，就转为一次正常变更。

```text
   ├─ specs/YYYY-MM-DD-<topic>.md      依据：需求 + 方案 + 计划 + 结果，保留
   ├─ deploy/                            常驻：部署形态、配置参考
   └─ operations/                        运维
      ├─ runbooks/{topic}.md             常驻，一个操作一份（模板自带几份）
      ├─ queries/{topic}.md              常驻，可复用的只读查询（不含凭据和客户数据）
      ├─ data-fixes/YYYY-MM-DD-*.md      依据：预演摘要、脚本、回滚脚本、执行留痕
      └─ incidents/YYYY-MM-DD-*.md       依据：事件与复盘，行动项回写到测试、闸门或 Runbook
不进仓库：缺陷三段式 → PR/MR 描述；验收截图 → MR 附件；发布说明 → Release 正文
```

`specs/`、`queries/`、`data-fixes/`、`incidents/`、`project/testing.md` 都在第一次有内容时才创建。

### 3.7 文档的格式与内容要求

适用于两层的全部文档：常驻文档、规格文档、Skill reference、运维记录。这一节取代 `documentation.md#编写规则` 的现有写法，并在框架仓库 `docs/README.md` 引用同一套规则。

**结构**

- 标题层级与内容从属一致：每份文档只有一个一级标题；`##` 是主题，`###` 是子主题，原则上不超过三级。
- 一节只讲一个主题；标题直接说出这一节的主题或结论，不用"概述""其他"这类空泛标题。
- 先写结论，再写依据：每节第一句给出规则或结论，原因和例外放在后面。
- 规格文档的一级章节固定为"需求、方案、计划、结果"；常驻文档按主题组织，不套模板。

**表达**

- 句子短，直陈事实；不铺垫背景，不写实现过程，不复述代码里能直接看到的内容。
- 多项并列、有对比关系的内容用表格；有先后顺序的内容用编号列表；其余用短段落。
- 每条规则都写得出"怎样算违反"；写不出判定方法的规则不写。
- 同一个概念全文使用同一个术语，首次出现时给出定义。
- 日期一律写绝对日期（2026-10-20），不写"上周""最近"。

**对 AI 友好**

- 区分两种路径：
  - **行内路径**：用反引号包住，按文档开头声明的基准（项目根或仓库根）解析；
  - **可点击链接**：保留合法的文档相对写法，或者用以 `/` 开头、按项目根或仓库根解析的写法。框架仓库版本可以注明这一写法由 `check-doc-references.py` 检查；业务项目版本不提这个仓库内部脚本。
- 规范文档不反向链接到 Skill。分发载荷里的文档只链接随同一交付面分发的文件，不链接根 `docs/` 或个人目录。
- 一行只写一段完整的意思，超过约 200 个字符时宜拆成列表或分句，方便按行读取和引用。这是编辑提示，不做检查。
- 一个事实只在一处维护，其他地方用链接加一句上下文，不复制正文。
- 常驻规范单份以约 10,000 个字符为精简提示值，超出时先删重复，再拆成专题文件；规格文档不设上限，但中档的需求一节宜控制在一屏左右。两项都是编辑提示，不做合规检查；已保留的历史规格不为统一格式而重写。

**权威落点**：本节规则写进 `template/.agents/skills/leistd-project-workflow/references/documentation.md#编写规则`，供业务项目使用；框架仓库的 `docs/README.md` 写同一套规则的仓库版本，两层各自引用本交付面里能访问到的文件。

**内容边界**

- 不写密钥、令牌、连接串、真实客户数据；运维记录里的样本数据要脱敏。
- 常驻文档只描述现状，不写"原来是……后来改成……"；演变过程写在规格文档里。
- 测试结果、命令输出、日志不写进文档；规格文档 §4 只写结论，并链接到 PR 或 CI。

### 3.8 与现有原则的差异（需要同步修改）

| 现有规定 | 改为 | 理由 |
| --- | --- | --- |
| `docs/README.md`：计划、评估完成即删 | 合并为 `docs/specs/`，保留 | 缺少依据就无法追溯取舍；与现行规则分开存放后，不会污染 AI 的默认上下文 |

| `documentation.md#编写规则` | 由 §3.7 取代，两层共用同一套规则 | 补上路径基准、行长、日期、术语等对 AI 友好的要求 |

## 8. 结果

### 与计划的偏差

- **不做镜像真实推送**：镜像失败会在首个项目推送时显式报错，不会产出错误产物；为此准备测试仓库，代价高于收益。远端权限、Registry digest 记为未实证。
- **不新建根 `AGENTS.md`**：规格位置已写在 `docs/README.md`、各仓库 Skill 和 Claude Code 启动钩子里，再加一个入口只会多一份需要同步的指针。
- **F-g 的实际收益**：
  - 整份 QA 文档从 20,783 字符降到 6,734 字符；
  - F1 任务实际读取的章节由 28,354 字符增至 29,450 字符，基本持平。
- **模板读取成本上限的累计增量**：

  | 场景 | 增量（字符） |

  | backend-crud | +1,810 |

- **GitHub 默认分支限制**：生成项目的 push 只对 main 生效，默认分支不是 main 时需要改 `ci.yml`；连续推送可能留下发布不完整的旧镜像对，部署按 digest 取。
