# 1.0.0 发布：指定版本与框架模板同号

状态：已完成 · 风险档：高 · 关联：https://github.com/zengqinglei/leistd-net/pull/133

## 1. 需求

### 问题

计划近期发布 `1.0.0` 正式版，并首发 `Leistd.Templates`。端到端核对发布流程发现：

1. **发不出 1.0.0**：`VERSION` 记录上一个正式版（`0.12.0`），下一版按提交递增，0.x 期间破坏性变更只升 Minor。按文档把 `VERSION` 改成 `1.0.0`，会被当作已发布版本继续递增，发出 `1.0.1` 或 `1.1.0`。
2. **未合回窗口**：正式 tag 打在 `main` 的回写提交上，合回 `develop` 之前，beta 会把已发布的提交再算一遍，推出低于已发布正式版或虚高的 beta。
3. **两个版本号**：模板版本独立于框架（首版 `0.1.0`），下游升级要分别查框架与模板版本的对应关系。

### 目标

- 维护者经一次 PR 显式指定下一版，beta 与正式版都按它发布，不手工打 tag。
- 未合回期间，beta 仍高于已发布正式版，且不重复计入已发布的提交；排队晚到的旧候选不得用旧源码发出更高版本。
- 框架与模板同号：`main` 上任一侧有变化，两侧都以同一版本发布；首发即 `1.0.0`。

非目标：Package Validation 等 API 兼容性基线（发布前由维护者另行决定）；自动把 `main` 合回 `develop`；develop 上模板单独改动触发框架 beta。

### 验收标准

均由 `scripts/test-workflow-change-scope.py` 覆盖，每条新判据都做过变异验证（去掉判据后对应测试失败）。

**指定版本**（`check_release_version_explicit`）

| # | Given | When | Then |
| --- | --- | --- | --- |
| 1 | 最高正式 tag `v0.12.0`，`VERSION` 改为 `1.0.0`，范围内有破坏性提交 | beta / stable 推算 | `1.0.0-beta.<N>` / `1.0.0` |
| 2 | `v1.0.0` 在未合回的 `main` 上（经合并提交进入），`develop` 新增 `feat` | beta 推算 | `1.1.0-beta.1`，只计未发布的提交 |
| 3 | 合回后新增 `fix`，再新增带脚注的破坏性提交 | stable 推算 | `1.1.0`，然后 `2.0.0` |
| 4 | `VERSION` 仍为 `0.12.0`，未合回的 `v0.13.0` 存在，新增 `fix` | beta 推算 | `0.13.1-beta.1` |
| 5 | 含旧候选 A 和一个修复的更新候选已发布 `v1.0.0`，A 的发布作业晚到 | stable 推算 | 推包前失败，列出 A 缺少的提交 |

**同号发布**（`check_template_channel_plan`、`check_template_release_version`、`check_template_existing_tag`、`check_template_release_notes`）

| # | Given（`main`） | Then |
| --- | --- | --- |
| 6 | 只改模板或打包项目 | 框架与模板都要求发布 |
| 7 | 只改框架 | 模板无变化，仍要求同号发布；发布说明写"模板无变更" |
| 8 | 只改内部文档 | 都不发布 |
| 9 | develop 上改模板 | 只验证不发布，也不触发框架 beta |
| 10 | 模板发布 | 版本取框架通道输出的正式版；缺失，或模板默认框架版本不等于它，即失败 |
| 11 | 计划里模板与框架发布责任不一致 | 计划校验失败 |
| 12 | 相邻两次发布：规划后上一轮的 `template-v*` 才落到祖先上 | 照常发布，上一版取上一轮的 tag |
| 13 | 重跑模板作业：本版本 tag 已推送且指向本次源提交 | 沿用 tag，只补缺的步骤；指向其他提交即停止 |
| 14 | 计划的模板基线不存在，或不是候选祖先 | 失败 |

### 已确认的决策

- 2026-10-20 用户确认实现显式指定版本，并要求从端到端视角审视闭环。
- 指定方式由提议的 `Release-As` 提交脚注改为修改 `VERSION`，见 §2。
- 2026-10-20 用户确认框架与模板同号，取代 2026-10-18 的"模板独立版本"。代价是主版本号表示"下游需要动手"，只改模板时框架会发布内容相同的版本。

## 2. 方案

### 现状事实

- `release.yml`「推算版本与 tag」：`git tag --merged HEAD` 取最高正式 tag 作范围起点，`Step-ReleaseVersion $VERSION $bump` 得到版本；范围读取全部提交，含模板提交。
- `scripts/release-commits.ps1` 的 `Get-ReleaseBump`：主版本为 0 时把 major 降为 minor。
- v0.12.0 的回写是手工把 `main` 合回 `develop`（`ff68faad`），文档未写这一步。
- `plan-quality-checks.py`：框架发布只看框架输入；模板通道自行判定，仅 push `main` 且模板有变化时发布，版本从 `template-v*` 独立递增。

### 设计

**版本推算**（`release.yml` 框架通道）

1. 最高正式 tag 取全部 `vX.Y.Z` tag，不要求是 HEAD 的祖先；`tag..HEAD` 对非祖先 tag 同样只取未发布的提交。
2. 前提是 `HEAD..tag` 除合并提交与版本回写外为空，即该 tag 发布的源码都在候选里，否则推包前停止。
3. `VERSION` 高于最高正式 tag：原样作为下一版（`bump=explicit`）；否则从两者中较高者按提交递增。

**同号发布**

- 计划（`plan-quality-checks.py`）：`stable` 上模板有变化时框架也要求发布；`TemplateRelease.Required` 恒等于 `ReleaseRequired`。校验（`quality-validation-plan.ps1`）拒绝两者不一致。
- 模板作业：`stable` 发布时版本取 `release` 作业新输出的 `version`，并断言模板默认的 `LeistdFrameworkVersion` 等于它；只验证时版本为 `<VERSION>-ci.<run>.<attempt>`；只改框架时发布说明写"模板无变更"。
- 模板作业的运行条件增加 `TemplateRelease.Required`（只改框架时模板无变化也要运行）。删除"框架被跳过时还原不等待"的分支：发布时框架必然已发布。
- 模板基线的时间语义：用计划冻结的 `BaseTag` 重算"有无模板变化"，不因规划后合法新增的 `template-v*`（相邻发布、本版本重跑）而失败；发布说明与升级闸门取低于本版本的最高祖先 tag。
- 重跑：目标 tag 已存在且指向本次源提交即沿用，跳过本地创建；同源包已在 nuget.org 时跳过推包（原有）；Release 由 action 按 tag 查找补齐。

**文档**：`docs/framework/versioning.md` 补「发布指定版本」三步与"发布后合回 develop"；`docs/template/versioning.md` 改为「版本与发布时机」；README 与生成项目的同步指南写明同号。

### 备选与取舍

| 决策 | 方案 | 取舍 |
| --- | --- | --- |
| 指定版本 | `Release-As` 提交脚注 | 写进历史后改不掉；只认非合并提交，PR diff 里看不到；要新增解析 |
| 指定版本 | **修改 `VERSION`（采用）** | 文档原本就这样描述；改错能再提 PR；不新增概念 |
| 模板版本 | 独立版本（原方案） | 语义纯粹，但下游要查两个版本号的对应关系 |
| 模板版本 | 主次版本一致、补丁独立 | 模板的破坏性变更只能藏进补丁号，语义失真 |
| 模板版本 | **完全同号（采用）** | 下游只认一个号；只改模板时框架发布内容相同的版本 |

### 兼容与回滚

- 正常的 stable 候选包含全部已发布源码，版本推算不变；排队晚到的旧候选由"撞已有 tag 才失败"改为一律在推包前停止。
- `develop` 只在未合回期间行为改变：beta 从已发布正式版以上递增；`main` 上有未合回的普通提交时停止发布，直到合回。
- 模板尚未发布过，同号没有存量迁移；首发即与框架同号。
- 框架已发布而模板作业失败时，只重跑模板作业；需要改代码时，由下一个同号版本补齐。
- 回滚即还原这次 PR，不涉及已发布的包与 tag。
