# 仓库维护文档

> 根 `docs/` 保存 leistd-net 仓库自身的维护规范与变更依据，不随 NuGet 包或 `dotnet new` 生成项目分发。文中反引号路径都相对仓库根。

| 文档树 | 职责 | 受众 | 分发方式 |
| --- | --- | --- | --- |
| `docs/` | 仓库架构、框架与模板维护规范、规格文档 | 仓库维护者 | 不分发 |
| `framework/docs/` | Leistd.* 公共 API、注册与运行时语义 | NuGet 使用者 | 随对应包分发 |
| `template/docs/` | 生成应用的工程规范与按需沉淀的项目文档 | 下游项目团队与 AI | 随模板生成 |

## 常驻文档与规格文档

常驻文档描述现行规则，默认读取；规格文档记录某次变更的依据，只在追溯时读取。两类分开存放，规格文档可以长期保留而不进入默认上下文。

| 类别 | 回答什么 | 何时读取 | 生命周期 |
| --- | --- | --- | --- |
| 常驻文档 | 系统现在是什么样、应该怎么做 | 默认读取，按索引路由 | 随代码同步修改，只描述当前状态 |
| 规格文档 | 某次变更为什么改、怎么定的、实际交付了什么 | 需要追溯时 | 一次变更一份，保留，不删除，不移动 |

### 常驻文档

| 位置 | 内容 |
| --- | --- |
| `docs/architecture/` | 跨框架、模板、Skill 和文档体系的长期原则与跨层决策 |
| `docs/framework/` | 框架开发、CI、版本与发布规范 |
| `docs/template/` | 模板维护、条件生成、验证与模板包发布规范 |
| `framework/docs/` | 公共契约，随 NuGet 分发 |
| `template/docs/` | 生成项目的工程规范，随模板分发 |

改了公共 API、注册方式、运行时语义或维护流程时，在同一个 PR 里更新对应的常驻文档；审查发现漏改按缺陷处理。

常驻文档只写当前决定、意图和规则，规则尽量指向对应的测试。不写"原来是……后来改成……"，演变过程、备选比较和评审经过写在规格文档里。

### 规格文档

一次变更只写一份规格文档，需求、方案、计划、结果是其中四节，按风险档逐级出现。跨 Framework、Template、Skill 的变更也只写一份，不在每个交付面复制。

**位置**：`docs/specs/YYYY-MM-DD-<topic>.md`；配图、报告等附件放进同名目录 `docs/specs/YYYY-MM-DD-<topic>/`。目录按日期自然排序，不另建索引。

**结构**：一级章节固定，便于检索和对比；章节内容不套模板，没有内容的章节和字段不写占位。

```markdown
# <主题>

状态：进行中 | 已完成 | 已废弃（被 <文件> 取代） · 风险档：中 | 高 · 关联：<PR 链接>

## 1. 需求    问题与背景；目标与非目标；功能要求 → 验收标准（Given/When/Then，注明由哪个自动化测试覆盖，或标"人工验收"）；
              非功能要求（有约束时）；待定问题与已确认的决策（谁、何时确认）
## 2. 方案    现状事实（附路径证据）；设计；备选与取舍（只列会改变边界的）；兼容与回滚
## 3. 计划    任务（每项写产物与验证方式）；不做的事
## 4. 结果    实际交付（PR 列表）；与计划的偏差及原因；验收记录；遗留项；已上收到哪些常驻文档
```

**按风险档写多少**：

| 风险档 | 规格文档 | 其他 |
| --- | --- | --- |
| 低：小修复、措辞、单点调整 | 不写 | 缺陷按"当前行为 / 期望行为 / 不应改变的行为"三段写在 PR 描述里 |
| 中：一般需求、一般缺陷修复、重构 | 写 §1 和 §4；方案用一段话写在 §1 末尾 | 计划只放在会话里 |
| 高：公共 API 或破坏性变更、数据模型与迁移、权限、跨层、发布流程 | 写全 §1–§4 | 不可逆的决策同时上收到常驻文档 |

计划只写到"任务 + 产物 + 验证"这一层。逐步骤的执行台账（checkbox 步骤、子代理进度）属于会话执行状态，放在 `.tmp/` 或 `.superpowers/`，不提交。

**生命周期**：

1. **创建**：需求确认时创建。用户请求或会话中已经明确的需求和授权直接写入 §1，视为已确认；只有真正待澄清的事项或新增的关键决定才停下来询问。
2. **更新**：决策变化时直接改原文，历史由 Git 保留，不另写修订记录。
3. **完成**：在完成变更的那个 PR 里填写 §4，状态改为"已完成"，并把仍然成立的规则上收到常驻文档。
4. **之后**：不删除，不移动，状态行是唯一标记；被新规格取代时状态改为"已废弃（被 <文件> 取代）"。

**紧急止损和热修**：先修复，不先写规格；修复 PR 合入时补一份简短规格，只写 §1 现象与原因和 §4 结果。

临时分析默认留在当前答复里，不落盘。

### 提交规则

| 文档 | 何时提交 |
| --- | --- |
| 规格文档 | §1 确认后即可单独提交，最迟随第一个实施 PR；§4 和状态随完成变更的那个 PR 提交 |
| 常驻文档 | 和对应的代码改动放在同一个 PR |
| 缺陷三段式、验收截图 | 写在 PR 描述或附件里，不落文件 |
| 会话执行状态（`.tmp/`、`.superpowers/`、子代理台账） | 不提交 |

交付前 `git status` 里不应再有未跟踪的 `docs/specs/` 或常驻文档；有则纳入提交，或在汇报里说明原因。何时提交以用户指示为准。交付汇报写明规格文档的状态，以及哪些常驻文档已经同步。

## 编写规则

适用于本仓库的全部文档：常驻文档、规格文档、Skill 及其 reference。

**结构**

- 每份文档只有一个一级标题；`##` 是主题，`###` 是子主题，原则上不超过三级。
- 一节只讲一个主题；标题直接说出主题或结论，不用"概述""其他"这类空泛标题。
- 先写结论再写依据：每节第一句给出规则或结论，原因和例外放在后面。

**表达**

- 句子短，直陈事实；不铺垫背景，不写实现过程，不复述代码里能直接看到的内容。
- 并列、有对比关系的内容用表格；有先后顺序的用编号列表；其余用短段落。
- 每条规则都写得出"怎样算违反"；写不出判定方法的规则不写。
- 同一个概念全文使用同一个术语，首次出现时给出定义。
- 日期写绝对日期（2026-10-20），不写"上周""最近"。

**对 AI 友好**

- 行内路径用反引号包住，按文档开头声明的基准（通常是仓库根）解析；可点击链接用文档相对写法，或以 `/` 开头、按交付根解析。两种写法由 `scripts/check-doc-references.py` 检查，`docs/specs/` 作为历史依据不检查。
- 规范文档不反向链接到 Skill；分发载荷只链接随同一交付面分发的文件，见[分发边界](#分发边界)。
- 一行只写一段完整的意思，超过约 200 个字符时宜拆成列表或分句。
- 一个事实只在一处维护，其他地方用链接加一句上下文，不复制正文。
- 常驻规范单份以约 10,000 个字符为精简提示值，超出时先删重复，再拆成专题文件；规格文档不设上限，但中档的需求一节宜控制在一屏左右。

行长与篇幅是编辑提示，不做检查；已保留的历史规格不为统一格式而重写。

**内容边界**

- 不写密钥、令牌、连接串和真实客户数据。
- 测试结果、命令输出、日志不写进文档；规格文档 §4 只写结论，并链接到 PR 或 CI。

## 分发边界

`framework/docs/`（随 NuGet 包）和 `template/`（随 `Leistd.Templates` 模板包与 `dotnet new`）是对外分发载荷，只写已经成立的公共契约与生成项目事实。已发布版本的升级契约属于公共契约：从某个已发布版本升级到另一个已发布版本时消费者必须做的事（框架包的发布说明与按需的升级指南，模板 `template-v*` 的 Release 正文与按需的升级说明，见[版本与发布规范](./framework/versioning.md#发布说明)与[模板版本与发布](./template/versioning.md#变更说明)），按版本写明即可。以下 leistd-net 仓库信息不得进入分发载荷，只留在根 `docs/`、根 `.agents/skills/` 与 Git：

- 候选方案、选型过程、实施计划、未实施方案，以及尚未发布的版本之间的迁移步骤；
- 分支、MR、提交、任务状态、阶段报告和历史结论；
- 仓库内部验证过程，以及 `.tmp/local-feed`、模板矩阵等仅供维护者使用的命令和路径；
- 尚未由当前源码和验证证明的未来技术栈或迁移说明。

实现完成后，只把已经成立的公共契约同步到 `framework/docs/`，把生成项目必须知道的工程事实同步到 `template/docs/`。各载荷自身包含什么由对应专项 Skill 说明。
