# 项目通用约定

本项目各端共同遵循的约定。后端具体规则见 [后端开发规范](./coding-backend.md)。
<!--#if (SpaFrontend)-->
前端具体规则见 [前端开发规范](./coding-frontend.md)。
<!--#endif-->

## 1. 语言与敏感信息

- 注释用中文；运行期异常与日志消息、测试诊断消息用英文；用户文案走本地化资源或英文默认文案。维护脚本面向人的输出不在此列。
- 名称与类型先表达职责；注释补必要契约、算法原因、并发与安全不变量、外部约束，不复述代码或记录修复过程。
- XML 注释不使用 Markdown 强调；代码用 `<c>`，API 引用用 `<see cref="..."/>`。
- 新增或修改的中文注释用中文标点；XML、JSDoc 摘要以句号结束，其他完整句同样处理；标识、路径和命令保留原样。
- 后端 XML 格式与覆盖要求见[文档注释](./coding-backend.md#文档注释)，前端按语言规范使用 JSDoc。
- 文档按主题分层，先当前用途与约束，再必要用法；同一事实一处维护，不写实施、评审和版本反复过程。
- 不硬编码密钥、令牌、密码或真实客户数据。
- 密钥、令牌、密码、连接串不进日志、响应与错误消息；日志也不记录邮箱、手机号、证件号等联系方式与身份信息，需要关联时记用户 Id。响应中的这类字段按项目规则脱敏。`BusinessException` 默认文案不拼这些值，要展示时经 `WithData` 交给词条。
<!--#if (IncludeOperationRecords)-->
- 数据库操作记录可保存业务失败词条所需的参数原值，包括联系方式；这是受权审计数据，不适用上一条日志不记联系方式的限制，日志、默认异常文案与原始异常文本的限制仍然适用。访问按查询/导出权限控制，保存与归档边界见[部署说明](../deploy/README.md#生产边界)。
<!--#else-->
- 操作记录写入结构化日志时只输出失败参数名 `OperationFailureDataKeys`，不要把参数原值另拼进日志。
<!--#endif-->
- 对外文案只写用户能采取的下一步。非敏感且确有帮助的输入可以回显（如已登录管理员操作中的订单号）；登录、找回密码等匿名场景不回显可用于枚举账号的用户名、邮箱。

## 2. Git 与提交

提交信息使用 Conventional Commits：`<type>(<scope>): <subject>`，常用 type 为 `feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore`。

## 3. 工程约束

### 3.1 开发前查找参考链路

实现新功能前，从现有代码选 1~2 个最接近的端到端链路（前端组件到持久化与迁移），沿用其分层、命名、目录、错误处理和 Mock 方式；存在疑问时以参考实现为准。

### 3.2 校验按规则归属分层

- 聚合自身的规则（各入口都要守）放**领域层**：只看本聚合状态的放实体方法；需经仓储读取的（唯一性、依赖外聚合状态）放领域服务，外聚合只读不改。
- 入口相关的放**应用层**：解析入参引用的外聚合（角色是否存在、默认角色）、协调多个聚合的修改。

### 3.3 验证在入口 DTO 层完成

字段验证在入口 DTO 完成，内层不重复校验；后端写法与例外见[后端开发规范 §5](./coding-backend.md#5-命名与-dto)。

### 3.4 新增能力优先扩展现有抽象

- 优先扩展现有抽象，无法承载时再新增接口；应用服务不直连外部 SDK 或客户端。
- 同一规则只有一条实现路径。

### 3.5 抽象在内层、依赖只向内

- 依赖方向与各层职责见[后端开发规范 §2](./coding-backend.md#2-分层与目录)。
- 内层需要外部能力或向外"下发"动作时，**在内层定中性抽象接口、由外层适配器实现**（依赖倒置），禁止内层直接引用外层类型。
- 反复出现的信封/载荷用**不可变值对象统一定义一次**，不散落多套。

### 3.6 删除幂等且保留真实失败

删除只将“不存在”视为成功；其他错误上抛，中止后续持久化，避免留下外部资源。

### 3.7 是否触达真实外部端由统一开关决定

外部或云端调用由统一开关（如 dry-run）决定，不由调用方传 opt-in 参数；不同入口行为一致。

### 3.8 枚举只在边界转换

- 领域内部状态用**强类型枚举**，不散裸字符串；**枚举 ↔ 对外契约串的转换只发生在边界**（序列化/handler 层），不下沉进领域、不上浮进无关层。
- **对外公开的分类值（`channel/mode/scope/type/status/outcome/severity` 之类）出入参与 JSON 命名策略一致**（camelCase：`orders`、`twoFactorRequired`、`succeeded`）；内部枚举 PascalCase，只在边界一处转换。DTO 字段直接用枚举类型交给宿主的 JSON 转换器，不手写 `ToString()`；查询串不经 JSON 转换器，按 camelCase 名称逐字校验后转换，数字与未定义值是该字段的验证错误；CSV 等非 JSON 输出在其边界写同一种名称。持久化的写法与对外契约无关，不随之迁移。
- 例外仅限**开放标识符**：由使用方定义、会落库或拼进键名的身份串，按定义原样传输，不随命名策略改写。当前只有通知类型与渠道名（如 `Security`、`InApp`、`Email`，参与偏好设置键 `Notifications.{类型}.{渠道}`）。例外不外扩：结果、状态这类封闭枚举不能套用。

### 3.9 接口/实现签名同步；导入用短名

- 接口与实现类**签名同步改**，不留漂移。
- 一律**文件顶部导入 + 用短名**，禁止在代码正文内联全限定命名空间；同名歧义用 `using` 别名。

### 3.10 项目决策项

DI 生命周期与注册方式见 [后端开发规范 §4](./coding-backend.md#4-依赖注入)；对象映射见 [后端开发规范 §6](./coding-backend.md#6-数据访问)。对不同外部系统的序列化命名风格按其契约在字段上显式标注。
