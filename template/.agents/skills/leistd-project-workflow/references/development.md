# 规划与实现

## 规格文档

按[风险档](quality.md#风险分档)决定写多少。规格文档把一次变更的需求、方案、计划和结果写在同一份文件 `docs/specs/YYYY-MM-DD-<topic>.md`，附件放同名目录。

| 风险档 | 规格文档 | 其他 |
| --- | --- | --- |
| 低 | 不写 | 缺陷按三段式写在 PR/MR 描述里 |
| 中 | 写 §1、§4；方案用一段话写在 §1 末尾 | 计划只放在会话里 |
| 高 | 写全 §1–§4 | 不可逆的决策同时上收到常驻文档 |

标题下第一行写 `状态：进行中|已完成|已废弃（被 <文件> 取代） · 风险档：中|高 · 关联：<PR/MR>`。一级章节固定为下面四节，内容不套模板；没有内容的章节和字段不写占位。

1. **需求**：问题与背景；目标用户与使用场景；目标与非目标；成功指标（能度量时）；功能要求与验收标准（Given/When/Then，每条注明覆盖它的自动化测试（未写时写计划位置），或标“人工验收”）；非功能要求（有约束时）；待定问题与已确认的决策（谁、何时确认）。有外部 PRD 时链接原文，只提炼这些要素。
2. **方案**：现状事实（附路径）；设计；只列会改变边界的备选与取舍；兼容与回滚。
3. **计划**：任务，每项写产物与验证方式；不做的事。逐步骤的执行台账属于会话状态，不提交。
4. **结果**：实际交付（PR 列表）；与计划的偏差及原因；验收记录（环境、版本、结论、验收人）；遗留项；已上收的常驻文档。

- **确认**：用户请求或会话中已明确的需求和授权直接写入 §1，视为已确认；只有真正待澄清的事项或新增的关键决定才停下来询问。
- **只要方案**：写到 §2 或 §3 为止，说明尚未实现。§4 在完成时才写。
- **更新**：决策变化时直接改原文。
- **完成**：在完成变更的 PR 里填写 §4、把状态改为“已完成”、把仍然成立的规则上收到常驻文档。之后不删除，不移动。
- **热修例外**：先止损和修复，事后补简短规格（风险档仍记为高，只写 §1、§4），见[环境交付](delivery.md)的热修通道。
- **与插件共存**：superpowers 等插件分开产出规格和计划时，都写进上述同一文件，计划写在 §3。何时提交服从用户指示。

缺陷三段式：当前行为、期望行为、不应改变的行为。

## 编码实现

1. 通过项目现有文档索引（及其任务读取清单）读取任务涉及的规范；分页排序与输入验证须读取 API 和后端规范中的对应章节。
2. 实施满足目标的最小完整改动，保持依赖方向、公共契约和错误处理一致。只在没有合理替代时引入新依赖，并说明收益、成本和风险；不硬编码密钥、令牌或真实客户数据。
3. 为新增或变化行为补充风险匹配的测试，不删除有效断言或静默跳过失败。
4. 修改 API、权限、持久化或前后端流程时，同时核对调用方、配置、Mock、迁移和拒绝路径。
5. 运行相关格式化、静态检查、构建、测试和必要的真实宿主验证。
6. 交付前核对 diff 是否触及业务规则或校验、状态流转、权限、对外契约、数据含义或用户可见流程（细则见[文档沉淀](documentation.md#何时更新常驻文档)）；触及的在同一 PR 更新或新建常驻文档，只写规格文档不算。汇报规格文档状态和已同步的常驻文档，只列有变化的项。

## 任务协调

1. 将工作拆成可独立验证且有明确依赖的步骤，只维护一个当前计划；完成一步后立即记录实际产物和验证证据。
2. 恢复中断任务时以当前分支、diff、测试和外部系统状态为准，不以旧计划状态代替事实。
3. 范围或关键决策变化时更新计划；没有真实证据的步骤不能标记完成。

不为任务协调创建 context、handoff、registry 或例行验收报告。

## 提交

用户要求提交时，先确认本次变更与工作区其他修改的归属，运行受影响检查，核对暂存区只包含当前任务，然后按项目现有提交规范提交并报告 SHA。提交不自动意味着推送或部署；若推送会触发流水线，先核对目标分支及影响，推送后跟进到明确结果，失败先按日志复现再修复。
