# 审查与测试

## 风险分档

- 低：文档、只改测试、界面小调、依赖小版本。
- 中：普通功能、后端逻辑、前端交互。
- 高：认证与权限、迁移、部署、框架大版本。

拿不准时往上取一档。各档跑哪些测试见 `docs/standards/testing.md#12-按开发场景选择范围`。

## 代码审查

默认不审查，交付时提醒用户可以审查，高风险改动一定提醒。用户要求审查时，由用户指定的审查方执行（任何 agent 或人）。

1. 确定审查基线、变更范围和相关规范，读取完整 diff 与受影响调用链。
2. 优先检查行为错误、边界条件、安全、权限、数据一致性、并发、兼容性、缺失测试和规范符合性（分层与职责归属、依赖方向、命名与目录）。
3. 先按严重程度列出 findings，每项含文件位置、影响、证据（规范类引用违反的条目与章节，其他给出预期行为与源码或测试证据）和修复建议。
4. 结论明确写“通过”或“不通过”；没有发现时列出未执行检查和残余风险。

不通过就修，修完再审，直到明确通过，不限轮数。审查覆盖最终 head 与基线。

只要求审查时不擅自实现功能。可运行最小检查确认 finding，但不把局部验证说成完整回归。

## 测试与故障定位

测试范围、执行时机与验证入口以 `docs/standards/testing.md` 和 `scripts/verify.ps1` 为准；两者缺失时从测试配置、CI 和现有用例确定入口。

1. 按变化行为、验收条件和风险选择单元、集成、端到端及手工验证范围。
2. 运行时语义用真实宿主或项目既有测试服务器验证。
3. 失败时保留命令和关键日志，区分产品缺陷、测试缺陷、环境问题和外部依赖；只修失败点，只重跑失败的用例和直接受影响的测试，不整条链重跑。
4. 补充测试时沿用现有框架、fixture 和断言风格，验证对外可观察行为及必要拒绝路径。
5. 汇总通过、失败、跳过、未覆盖范围和残余风险。

不得删除有效断言、静默跳过失败、伪造依赖或把未执行测试写成通过。

证据只在覆盖当前输入时有效：相关源码、依赖、配置、fixture 或平台变化后重新验证，仍有效时不重复执行。记录命令、范围、环境和实际结果，不把旧程序集、另一候选或缺失的 CI 当作已通过。等待 CI 时在后台运行 `gh run watch <id> --exit-status` 靠完成通知唤醒，期间推进不依赖它的工作，不写 sleep 轮询。
