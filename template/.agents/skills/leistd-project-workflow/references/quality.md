# 审查与测试

## 代码审查

1. 确定审查基线、变更范围和相关规范，读取完整 diff 与受影响调用链。
2. 优先检查行为错误、边界条件、安全、权限、数据一致性、并发、兼容性、缺失测试和规范符合性（分层与职责归属、依赖方向、命名与目录）。
3. 先按严重程度列出 findings，每项含文件位置、影响、证据和修复建议：规范类引用违反的具体条目（文件与章节），其他给出预期行为与源码或测试证据。
4. 没有发现时明确说明，列出未执行检查和残余风险。

完整改动形成后审查代码与文档一致性，可与 CI 并行，高风险难返工的边界可提前审查；修复后复核 finding 与新增提交的影响，不重复未变化部分。审查覆盖最终 head、基线及后续增量；核对 CI 执行的候选与 head/base 对应，base 更新后重新验证合并结果。

只要求审查时不擅自实现功能。可运行最小检查确认 finding，但不把局部验证说成完整回归。

## 测试与故障定位

测试范围、执行时机与验证入口以 [docs/standards/testing.md](../../../../docs/standards/testing.md) 和 [scripts/verify.ps1](../../../../scripts/verify.ps1) 为准；两者缺失时从测试配置、CI 和现有用例确定入口。

1. 按变化行为、验收条件和风险选择单元、集成、端到端及手工验证范围。
2. 先跑最小相关测试，再按影响面扩大；运行时语义用真实宿主或项目既有测试服务器验证。
3. 失败时保留命令和关键日志，区分产品缺陷、测试缺陷、环境问题和外部依赖；先复现目标失败，修复后扩大回归。
4. 补充测试时沿用现有框架、fixture 和断言风格，验证对外可观察行为及必要拒绝路径。
5. 汇总通过、失败、跳过、未覆盖范围和残余风险。

不得删除有效断言、静默跳过失败、伪造依赖或把未执行测试写成通过。测试结果留在答复与 CI；形成长期测试规则或重复操作时才更新权威文档。

复核可信且覆盖当前输入的证据；相关源码、依赖、配置、fixture 或平台变化后重新验证。记录命令、范围、环境和实际结果，不把旧程序集、另一候选或缺失的 CI 当作已通过。证据仍然有效、也没有新的验证需要时，不重复执行相同的验证。等待 CI 时在后台运行 `gh run watch <id> --exit-status` 靠完成通知唤醒，期间推进不依赖它的工作，不写 sleep 轮询。
