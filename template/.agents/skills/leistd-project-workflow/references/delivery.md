# 环境交付

先确认目标环境、产物版本和用户要求的阶段。优先参考项目部署文档及最近同类交付；缺失时从实际流水线、产物、配置、迁移入口和健康检查建立事实。

## 部署步骤

1. 核对候选提交、产物组成与版本对应关系、配置和密钥来源、成功判据及回滚条件；涉及数据时核对备份、兼容性和恢复能力。
2. 按当前项目确认部署与迁移顺序；存在自动迁移时不重复执行，旧版本并行运行时核对兼容性。
3. 外部操作前核对现有授权是否覆盖目标、环境和动作；未覆盖时再询问。按项目流程执行，并验证产物版本、健康、日志、数据状态与核心业务路径。
4. 失败时依据实际状态保护数据并恢复；应用回滚与数据恢复分别判断。报告版本、环境、验证结果和未解决风险。已验证且会复用的环境规则更新到项目部署文档，并登记到现有文档索引。

## 环境晋级

- 测试、预发和生产部署同一份不可变产物：镜像按 digest、包按版本号晋级，不按环境重新构建。提交 SHA 标签可以被改写，只用于查找，不作为部署身份。
- 环境之间只有配置和机密不同，构建输入相同。
- 构建与推送产物的流水线、环境清单和部署入口以项目部署文档和实际流水线为准。项目流水线还没有产出不可变产物时，在交付汇报里写明这一缺口，不把手工构建的产物当作已晋级。

## 测试环境验收

按项目测试规范的测试环境验收执行：有规格时依据 §1、结论写进 §4；低档没有规格的，依据已确认的请求或 PR/MR 的预期行为，结论写在 PR/MR。

## 生产与配置变更

- 生产部署、迁移和回滚由人确认后执行。AI 准备候选版本（digest）、变更清单、迁移与回滚方案；确认前不执行。
- 配置或运维变更同样先确认：改哪个键、在哪里改、如何生效（是否重启）、如何验证、如何恢复。执行后验证新值已生效。

## 热修通道

紧急故障先止损，不先写规格：

1. **止损**：先判断本次发布是否已执行迁移，以及上一版本能否运行在当前库结构上。
   - 兼容：回滚到上一个已验证的 digest，或关闭对应开关；
   - 不兼容：回滚镜像无效，按实际兼容问题选择前滚修复、经验证的兼容结构调整（如适用时补默认值）或恢复方案，涉及库的操作按[运维操作](operations.md)的数据修正顺序执行；
   - 数据已受损：同样按数据修正处理。
2. **修复**：从生产当前版本对应的提交拉分支，只做最小修复，跑与改动相关的最小验证。修复同时合回主干，避免下次发布丢失。
3. **发布**：按“生产与配置变更”由人确认后发布。
4. **事后**：补简短规格，只写 §1 现象与原因、§4 结果（写法见[规划与实现](development.md)）；补回归测试；需要复盘时按[运维操作](operations.md)的事件与复盘处理。

## 发布说明

- 发布说明写在 Release 正文（或项目指定的发布记录），不另建文件。
- 由 AI 从本次合入的 PR/MR 和规格文档自动聚合，改写成面向用户的语言：用户能感知的变化、需要用户或运维配合的动作、已知问题；不写内部实现。
- 由人审阅后发布。
