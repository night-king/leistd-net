# 文档沉淀

## 常驻文档与依据文档

现行规则和变更依据分开存：AI 默认只读常驻文档，需要追溯“为什么”时才读依据文档。

| 类别 | 回答什么 | 何时读取 | 生命周期 |
| --- | --- | --- | --- |
| 常驻文档 | 系统现在是什么样、应该怎么做 | 默认读取，按项目文档索引路由 | 与代码在同一 PR 修改，只描述当前状态 |
| 依据文档 | 某次为什么改、怎么定的、交付了什么 | 需要追溯时 | 一次一份，保留，不删除，不移动 |

## 信息归属

| 信息 | 权威位置 | 类别 |
| --- | --- | --- |
| 项目工程规则与决策 | `docs/project/{topic}.md`；决策记录只追加，失效时标注被取代 | 常驻 |
| 业务规则，按主题 | `docs/requirements/{topic}.md` | 常驻 |
| 模块边界、模型和对外契约 | `docs/modules/{module}/README.md` | 常驻 |
| 部署形态、环境与配置 | `docs/deploy/` | 常驻 |
| 运维手册、可复用的只读查询 | `docs/operations/runbooks/{topic}.md`、`docs/operations/queries/{topic}.md` | 常驻 |
| 一次变更的需求、方案、计划、结果 | `docs/specs/YYYY-MM-DD-<topic>.md`，写法见[规划与实现](development.md) | 依据 |
| 数据修正、事件与复盘 | `docs/operations/data-fixes/YYYY-MM-DD-<topic>.md`、`docs/operations/incidents/YYYY-MM-DD-<topic>.md`，写法见[运维操作](operations.md) | 依据 |
| 发布说明 | Release 正文 | 不落文件 |
| 缺陷三段式、验收截图 | PR/MR 描述或附件 | 不落文件 |
| 团队或合规要求的报告 | 沿用最新同类记录；没有先例时建立最小规则和对应目录 | 按要求 |

`docs/standards/` 若是项目模板提供的规范基线（项目索引会写明），随模板版本整体更新：项目规则不写进去，写入 `docs/project/`，与基线冲突时以项目规则为准。

这些路径表达信息所有权，目录在第一次有内容时创建，不预建（模板自带的 `docs/deploy/`、`docs/operations/runbooks/` 除外）。项目已有不同且清晰的结构时沿用现状。常驻文档默认更新同一主题文件；新文档登记到项目文档索引，依据文档不登记，按日期自然排序。

## 何时更新常驻文档

改动触及下列任一项时，在同一个 PR 里更新对应的常驻文档（`requirements/`、`modules/` 或 `project/`）：

1. 业务规则或校验：取值范围、计算口径、唯一性、额度、时限；
2. 状态，以及状态之间的流转条件；
3. 权限：权限点、角色可见范围、租户隔离；
4. 对外契约的业务含义：错误码含义、事件、导入导出格式，以及会改变调用方行为的接口规则。字段本身以接口定义和代码为准，不抄进文档；
5. 数据含义：新增字段，或现有字段的业务含义改变；
6. 用户可见的流程：步骤、入口、通知。单个界面控件（如新增一个筛选框）不算流程变化。

对应主题还没有常驻文档时，触及上述条件就新建一份。

常驻文档只写意图和规则，不复述代码一眼能看出的内容，规则尽量指向对应的测试。审查发现漏更新时按缺陷处理。

## 提交规则

| 文档 | 何时提交 |
| --- | --- |
| 规格文档 | §1 确认后可单独提交，最迟随第一个实施 PR 提交；§4 和状态随完成变更的 PR 提交 |
| 常驻文档 | 与对应的代码改动在同一个 PR |
| 缺陷三段式、验收截图 | 写在 PR/MR 描述或附件里，不落文件 |
| 会话执行状态（计划台账、子代理进度） | 不提交 |

交付前 `git status` 里不应留有未跟踪的规格文档或常驻文档；有的话纳入提交，或在汇报里说明原因。何时提交以用户指示为准。

## 编写规则

适用于常驻文档、规格文档、Skill reference 和运维记录。

**结构**

- 每份文档只有一个一级标题；`##` 是主题，`###` 是子主题，原则上不超过三级。
- 一节只讲一个主题；标题直接说出主题或结论，不用“概述”“其他”这类空泛标题。
- 每节第一句给出规则或结论，原因和例外放在后面。
- 规格文档的一级章节固定；常驻文档按主题组织，不套模板。

**表达**

- 句子短，直陈事实；不铺垫背景，不写实现过程，不复述代码里能直接看到的内容。
- 并列且有对比的内容用表格，有先后顺序的用编号列表，其余用短段落。
- 每条规则写得出“怎样算违反”；写不出判定方法的不写。
- 同一概念全文用同一术语，首次出现时给出定义。
- 日期写绝对日期（如 2026-10-20），不写“上周”“最近”。

**对 AI 友好**

- 行内路径用反引号包住，按文档开头声明的基准（通常是项目根）解析；可点击链接用文档相对写法，或以 `/` 开头、按项目根解析。
- 规范文档不反向链接到 Skill；只链接仓库内的文件，不链接个人目录。
- 一行只写一段完整的意思，超过约 200 字符时宜拆成列表或分句。
- 一个事实只在一处维护，其他地方用链接加一句上下文，不复制正文。
- 常驻规范单份以约 10,000 字符为精简提示值，超出时先删重复，再拆成专题文件。规格文档不设上限，中档的需求一节宜控制在一屏左右；已保留的历史规格不为统一格式重写。

**内容边界**

- 不写密钥、令牌、连接串和真实客户数据；运维记录里的样本数据脱敏。
- 常驻文档只描述现状，不写“原来是……后来改成……”；演变过程写在规格文档里。
- 测试结果、命令输出和日志不写进文档；规格文档 §4 只写结论，并链接到 PR 或 CI。

## 规范演进

项目规范在开发中持续积累与精简，由项目文档（`docs/project/`）承载；本 Skill 保持与技术栈无关，不写入项目规则。

- **沉淀阈值**：同类纠正或审查意见第二次出现时沉淀为规则。用户明确的决定、首次确认的重要契约、会导致重大错误的规则可以首次沉淀。
- **优先闸门**：判据稳定、自动化收益成立的规则补 lint、测试或脚本检查；文档保留原因、适用范围和例外，并写明闸门实际检查什么。
- **同步精简**：写入时核对目标文档与本任务引用的规范，修正过时条目，合并重复要求，删除可由代码或闸门直接表达的内容。实施任务直接修正，只读任务报告候选；只汇报有实际变化的结论。
- **登记入口**：新文档或拆分出的专题登记到项目文档索引，有任务读取清单时同步更新。
