# 文档沉淀

## 创建判断

依次确认：

1. 是否已有同主题的权威文档？
2. 信息是否已经由源码、测试、配置、Git 或 CI 清楚表达？
3. 是否经过当前实现或验证确认，并会被跨会话、跨成员或重复使用？
4. 新文档的维护收益是否高于漂移成本？

优先更新最新且有效的同类文档。没有同类文档但满足长期沉淀条件时主动创建，不因目录缺失而跳过；归属或业务决策无法从事实确定时再询问用户。

## 信息归属

| 信息 | 建议权威位置 |
| --- | --- |
| 跨需求工程规则 | `docs/project/{topic}.md` |
| 长期需求决策与验收边界 | `docs/requirements/{topic}.md` |
| 稳定模块边界、模型和对外契约 | `docs/modules/{module}/README.md` |
| 可重复但无法由脚本表达的操作 | `docs/guides/{area}/{topic}.md` |
| 环境、发布和运维事实 | `docs/deploy/README.md` 或环境主题文件 |
| 团队或合规明确要求的报告 | 沿用最新同类记录；没有先例时建立最小报告规则和对应目录 |

`docs/standards/` 若是项目模板提供的规范基线（项目索引会写明），随模板版本整体更新：项目规则不写进去，写入 `docs/project/`，与基线冲突时以项目规则为准。

这些路径表达信息所有权，不要求预建完整目录。项目已有不同且清晰的结构时沿用现状；已有文档索引则登记入口，没有索引时仅在文档超过一个或入口不明确时建立。

## 编写规则

- **结构化清晰、标题层次分明、内容简洁明了**：按逻辑分节，标题层级（`#`/`##`/`###`）与内容从属关系一致；一节只讲一个主题，句子精炼、直陈结论，不铺陈。
- 一个事实只维护一处，其他位置使用链接。
- 标题直接表达主题，只保留结论、边界、执行步骤和验证方式等必要内容。
- 不复制背景、实现流水、命令输出、空字段或可由代码直接获得的清单。
- 不套固定规范、需求、计划或报告模板；参考最新有效的同类文档。
- 默认更新同一主题文件。只有必须按时间保留的事件记录才使用日期或版本前缀。
- 不记录密钥、令牌、真实客户数据或其他敏感值。

实现经过、审查 findings、测试结果和部署日志默认留在答复、Git、PR、CI 或平台日志中，不为每次任务生成报告。

## 规范演进

项目规范在开发中持续积累与精简，由项目文档（`docs/project/`）承载；本 Skill 保持与技术栈无关，不写入项目规则。

- **沉淀阈值**：同类纠正或审查意见第二次出现时沉淀为规则。用户明确的决定、首次确认的重要契约、会导致重大错误的规则可以首次沉淀。
- **优先闸门**：判据稳定、自动化收益成立的规则补 lint、测试或脚本检查；文档保留原因、适用范围和例外，并写明闸门实际检查什么。
- **同步精简**：写入时核对目标文档与本任务引用的规范，修正过时条目，合并重复要求，删除可由代码或闸门直接表达的内容。实施任务直接修正，只读任务报告候选；只汇报有实际变化的结论。
- **控制篇幅**：单份核心规范以约 10,000 字符为精简提示值；超出时先删重复与冗长示例，再把只在特定任务需要的主题拆为专题文件。
- **可判定**：每条规则写得出怎样判定违反；写不出的不沉淀。
- **登记入口**：新文档或拆分出的专题登记到项目文档索引，有任务读取清单时同步更新。
