# 下游反馈

文中路径都相对仓库根。下游项目（消费 `Leistd.*` 包或由模板生成的业务项目）以反馈文件或 issue 提出问题和建议时，按本文处理：每轮反馈写一份规格文档，结束时给下游一份回执。

## 流程

1. **接收**：读全反馈文件或 issue，逐项编号；下游已有编号时沿用。在 `docs/specs/YYYY-MM-DD-<topic>.md` 建本轮规格，§1 列出全部条目。下游给出的现象、日志和实测数据先核对再引用，不直接当作结论。
2. **归层**：按下文"归层"逐项判定落位层，一项涉及多层时拆开分别判定。
3. **决定**：逐项采纳或不采纳，按 `docs/architecture/design-principles.md#5-变更取舍原则` 取舍，理由写进规格 §1。
4. **排期**：用 `gh pr list --state open` 和进行中的规格核对在途改动。与在途改动修改同一契约、存在实际冲突或依赖的项，等在途改动合入后再开始，或并入同一个 PR；只是触及同一文件的不同段落不必等待；互不依赖的项可以分 PR 并行。
5. **实施**：按落位层使用对应专项 Skill；跨层时由本 Skill 统筹。缺陷类条目先写修复前失败的回归测试。
6. **回执**：按下文"回执"写给下游，同时填写规格 §4、状态改为"已完成"。
7. **通知**：把回执交到下游指定的位置（通常与反馈文件同目录），或作为 issue 回复，附 PR 与版本链接。随后的版本发布按 `docs/framework/versioning.md#发布说明` 另行通知。

## 归层

| 层 | 判定 | 落位 | 负责 Skill |
| --- | --- | --- | --- |
| 框架 | 通用能力、公共 API 或运行时语义的缺陷与缺口，换一个下游也会遇到 | `framework/`、`framework/docs/` | `developing-leistd-framework` |
| 通用 Skill | 与技术栈无关的协作流程和纪律 | `template/.agents/skills/leistd-project-workflow/` | `developing-leistd-template` |
| 模板规范 | 生成项目的代码、配置、CI 和 `template/docs/standards/` 基线 | `template/` | `developing-leistd-template` |
| 项目级 | 只在该项目成立：业务规则、项目自有的基础设施、脚本与流水线 | 留在下游，回执中说明理由 | 不在本仓库实施 |

拿不准该归框架、模板还是项目时，问"第二个下游是否会遇到同样问题"：会，就上收到框架或模板；不会，就留在项目级。

## 决定的写法

- **采纳**：写明落位层和修法，修法指向规范或测试，不复述代码。
- **不采纳**：理由能让下游复核，即引用现行规范、实测数据，或写明代价超过收益；会随条件变化的，写明何时重新评估。
- **有分歧**：下游的判断与本仓库不一致时单独回应，说明保留或调整了什么，以及依据。

## 回执

回执给下游阅读，按以下四节写，不写本仓库的评审经过和执行台账：

| 节 | 内容 |
| --- | --- |
| 对应反馈 | 反馈文件或 issue；已合入的 PR 和合并提交 |
| 结论 | 采纳与不采纳的项数；采纳表（编号、内容、落位层、修法）；不采纳表（项、理由）；分歧回应 |
| 版本节奏 | 影响哪个交付面（框架包、模板包、Skill），进入哪个通道和版本，还有哪些发布步骤需要单独授权 |
| 下游需要同步的项 | 逐项写下游要做什么；下游已经自行落地的写"无需改动"；需要手工吸收的给出入口 |

## 边界

- 规格和回执不写下游的客户数据、凭据和内部系统细节，只写抽象后的问题。
- 分发载荷（`framework/docs/`、`template/`）不出现下游项目名称或反馈轮次，见 `docs/README.md#分发边界`。
- 不承诺未授权的发布时间；合入 `main` 和正式版发布按 `docs/framework/versioning.md#需单独授权的发布操作` 单独授权。
